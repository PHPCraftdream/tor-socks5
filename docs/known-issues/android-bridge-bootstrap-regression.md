# Android: fresh bridges stop bootstrapping after a binary update

## Симптом

До обновления бинарника приложение подключалось. После обновления те же
свежие bridge lines не подключались на телефоне, хотя они проходили проверку в
`C:\Users\Computer\Desktop\resocks5\tor-socks5`. Ошибка не была связана с
пустым или устаревшим пулом: на телефоне был проверен минимальный набор из
трёх мостов, которые на десктопе успешно проходили obfs4 и TLS.

## Наблюдение на телефоне

Для исключения ошибки ранжирования активного пула был временно оставлен только
этот набор:

```text
obfs4 51.79.88.193:45529 ...
obfs4 77.243.189.234:5443 ...
obfs4 185.177.207.243:11243 ...
```

Arti на Android успешно доходил до запуска obfs4-потоков, SOCKS-handshake и
TLS-handshake. Затем примерно через 10–12 секунд каждый fetch bridge
descriptor завершался строкой:

```text
tor_dirmgr::bridgedesc: download failed for "<bridge>": Programming error
```

После этого остаётся `Fetching consensus` на 8%, потому что мост не получает
descriptor и остаётся `dir_info_missing`/`unsuitable to purpose`.

## Точная причина регрессии

В предыдущем исправлении `e0b9334` в vendored `tor-dirmgr` был добавлен общий
тайм-аут fetch bridge descriptor в **10 секунд**. Для холодного obfs4-канала
этого недостаточно: TCP, SOCKS и TLS уже могут завершиться, а ответ с
descriptor ещё не успевает прийти. Тайм-аут преобразовывался в
`tor_error::Bug`, поэтому наружу показывалось вводящее в заблуждение
`Programming error`, а ошибка считалась фатальной и не планировалась на
повторную попытку.

Это объясняет, почему до обновления работало и почему ручная проверка мостов на
десктопе успешна: сами bridge lines исправны, ломается только Android-путь
получения descriptor после изменения бинарника.

## Исправление

В `vendor/tor-dirmgr/src/bridgedesc.rs`:

1. Тайм-аут fetch увеличен с 10 до 30 секунд. Ограничение сохраняется, чтобы
   зависший мост не блокировал очередь, но холодному obfs4-каналу даётся
   реальное время на ответ.
2. Тайм-аут теперь возвращается как `RequestFailedError` с
   `RequestError::DirTimeout`, а не как `tor_error::Bug`. Это даёт корректную
   диагностику (`Request failed ... directory timed out`) и позволяет Arti
   повторить попытку по обычной transient-схеме.

Проверка компиляции: `cargo check -p tor-dirmgr` проходит.

Отдельно обнаружилось, что полностью чистый Arti-кэш не успевает получить
первый consensus за прежние 75 секунд: канал и circuit уже создаются, но
загрузка consensus продолжается. Поэтому Android bootstrap attempt увеличен
до 300 секунд, а watchdog неподвижного прогресса — до 120 секунд. Это не
оставляет зависание бесконечным, но не обрывает нормальный cold start на
медленном bridge.

## Важное ограничение диагностики

Активный пул из 30 мостов по-прежнему выбирается по TCP-метаданным. TCP probe
не доказывает, что obfs4/TLS и получение descriptor работают. Поэтому после
проверки исправления полный фоновый список нужно восстановить, а список
активных мостов формировать по результатам глубокого канального теста, не
удаляя большой фоновый пул.

Во время эксперимента телефонный файл bridge lines временно заменялся тремя
строками; перед обычной эксплуатацией необходимо вернуть сохранённый полный
список (`phone-bridges-merged.txt`) и отдельно восстановить
`tor-socks5.alive-bridges.log`.

## Что было сделано в этой сессии

1. Проверен полный путь на телефоне: Java service → Android FFI → Arti →
   `tor-dirmgr` → managed `obfs4` PT.
2. Временный список из 7670 мостов был сужен до трёх bridge lines, которые в
   этот же день успешно прогревались в десктопном `tor-socks5`.
3. Зафиксировано, что Android проходит SOCKS handshake и TLS handshake; это
   исключает отсутствие PT-бинарника и обычную TCP-недоступность мостов.
4. В `tor-dirmgr` исправлен слишком короткий 10-секундный descriptor timeout:
   установлен лимит 30 секунд, а timeout переведён из `Programming error` в
   повторяемый `RequestFailed(DirTimeout)`. `cargo check -p tor-dirmgr` прошёл.
5. Собрана и установлена debug APK с этим исправлением. В логах вместо ложного
   `Programming error` появилась честная `Directory request failed`.
6. Для проверки кэша каталог `files/tor/arti-data` не удалялся, а был
   переименован на телефоне в `arti-data.debug-before-reset`; затем приложение
   создало чистое состояние. Резерв можно вернуть обратно после остановки
   приложения.
7. На чистом состоянии подтверждено: один из трёх мостов завершает Tor
   handshake и строит circuit (`Completed handshake`, `Circuit creation
   success`). Затем Arti начинает получать consensus, но старый общий лимит
   bootstrap в 75 секунд истекает раньше завершения cold start.
8. В исходнике Android FFI лимит изменён с 75 до 300 секунд, а watchdog
   неподвижного bootstrap-прогресса — с 45 до 120 секунд. APK с этими двумя
   последними изменениями ещё **не собран и не установлен**: запуск Gradle был
   остановлен по запросу.

## Текущее состояние и полученный вывод

Корень первоначальной регрессии доказан: 10-секундный timeout descriptor
ошибочно маскировал сетевой timeout под `Programming error` и запрещал retry.
Это исправлено в исходнике и проверено на устройстве.

Полное подключение пока не подтверждено, потому что холодная загрузка consensus
не укладывается в прежние 75 секунд. Это уже отдельная проблема времени
ожидания cold start, а не доказательство неисправности свежих мостов. Десктоп
на тех же трёх мостах продолжает работать за счёт уже прогретого состояния.

На момент остановки диагностики телефон оставался на экспериментальном списке
из трёх мостов. Большой фоновый список не удалён: его сохранённая копия лежит
локально в `phone-bridges-merged.txt`; резерв Arti-state находится на телефоне
в `files/tor/arti-data.debug-before-reset`.

## Варианты следующего шага

### Вариант A — продолжить текущий фикс

Собрать APK с лимитом 300 секунд, установить поверх debug-сборки и дать чистому
состоянию закончить первый consensus. После успешного cold start проверить
живой запрос через SOCKS, затем вернуть полный список мостов и сохранить
состояние.

### Вариант B — восстановить старое состояние

Остановить сервис, переименовать созданный чистый `arti-data` в резерв и вернуть
`arti-data.debug-before-reset` обратно. Это быстрее проверит, достаточно ли
кэшированного consensus для обычного запуска, не удаляя пользовательские
данные.

### Вариант C — изменить архитектуру cold start

Не считать получение consensus одним 75/300-секундным событием: оставить Tor
bootstrap работающим дольше, показывать в UI отдельный честный статус
`Fetching consensus`, а активный пул обновлять после первого успешного
descriptor/circuit. Это уменьшит вероятность повторной потери прогресса на
медленных мобильных сетях.

### Вариант D — улучшить выбор активных мостов

TCP probe оставить только фильтром фонового пула. Для активной тридцатки
использовать глубокий PT/Tor channel test и хранить его результат отдельно от
7670 bridge lines. Тогда хорошие мосты из десктопного health store не будут
вытесняться только из-за низкого TCP-рейтинга на телефоне.
