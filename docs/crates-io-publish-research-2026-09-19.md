# Publishing tor-socks5 to crates.io — research report

Date: 2026-09-19. Read-only research; no files besides this one were changed.

## Executive summary

**Verdict: not publishable as-is today; conditional yes with a phased plan.** Two independent blocker classes exist, and they are not the same size. The first is a pure hygiene bug: all 26 internal workspace path dependencies (`path = "../X"`) across every `packages/*` and `apps/*` crate omit the `version` field Cargo requires for publishing — `cargo publish` will hard-fail on every one of them with "all dependencies must have a version specified" until fixed. That is a day of mechanical work, not a design problem. The second, real blocker is architectural: `arti-wrapper`, and everything that depends on it (`bridge-fetcher`, `android-ffi`, `apps/socks5-proxy`), pulls in six-of-seven `[patch.crates-io]`-overridden crates (`Cargo.toml:87-118`). Cargo strips `[patch]` sections when packaging a crate and does not propagate them to consumers — confirmed via the Cargo Book and two matching upstream Cargo issues (rust-lang/cargo#13222, rust-lang/cargo#10440, the latter describing the identical `tectonic_engine_spx2html`/`pinot` scenario). This is not a hard "cargo will refuse to publish" blocker — it is a silent-regression blocker: a freshly `cargo add`ed `arti-wrapper` on Windows would resolve plain crates.io `saturating-time` 0.3.0 and hit the exact 100%-CPU infinite loop in `SystemTime::saturating_add` that this project's own fork exists to fix (`vendor/README.md:17-25`, `docs/upstream-reports.md:26-113`). The good news: **7 of the 10 `packages/*` crates never touch `arti-client`/`tor-*` at all** (`persist-lock`, `bridge-verify-core`, `auth`, `bridge-probe`, `bridge-store`, `proxy-config`, `socks5-proto`) and could publish today once the version-field hygiene fix lands — no vendor entanglement whatsoever. Licensing is clean: every vendored upstream (Tor Project's `arti`/`tor-*` crates, and `saturating-time`) is dual `MIT OR Apache-2.0`, matching this workspace's own license, independently confirmed against the live crates.io registry. `android-ffi` is correctly out of scope for "SDK on crates.io" — it is `crate-type = ["cdylib"]` only (`packages/android-ffi/Cargo.toml:15-17`), produces no rlib, and is not something another Rust crate can `use`; it belongs on an Android/JNI distribution channel, not crates.io. Of the vendored fixes, three (`saturating-time`, `tor-dirclient`, and one of `tor-dirmgr`'s three fixes) already have hand-written, ready-to-send patches sitting in `docs/upstream/` — sending those costs nothing and is the highest-leverage next step; `tor-circmgr`'s bandwidth-floor patch, by contrast, is explicitly documented by this project as a permanent, anonymity-trading local fork that "would be unacceptable in upstream Tor/arti" (`docs/circuit-speed-plan.md:6-8`) and will never be a candidate for upstreaming.

## 1. Can `[patch.crates-io]` ship in a published crate?

**Short answer: mechanically yes (`cargo publish` does not refuse to run because your workspace has a `[patch]` section), but the patch never reaches downstream consumers.** This is confirmed, not guessed, from three independent sources:

- **Cargo Book, "Overriding Dependencies"**: "Cargo only looks at the patch settings in the `Cargo.toml` manifest at the root of the workspace. Patch settings defined in dependencies will be ignored." `[patch]` transitivity is scoped to *within one workspace* — a binary's root `[patch.crates-io]` applies to a path/git library dependency's `uuid` usage too, but only because the *binary's own* workspace root declared it, never because the library itself shipped one.
- **rust-lang/cargo#6535** ("Having a `[patch]` section when publishing is not an error"): long-standing, deliberate design — `cargo package`/`publish` normalizes the manifest and **removes the `[patch]` section** from what gets uploaded. Even if it somehow survived, only the *top-level* consumer's `[patch]` section is ever honored, per the point above.
- **rust-lang/cargo#13222** and **rust-lang/cargo#10440**: two real-world reports of exactly this project's situation. #13222 is a library author who forked `rustls` and found "any library crate that depends on this fork cannot be published because crates.io doesn't support patch directives" (closed as "not planned" — Cargo's team does not consider this solvable at the tooling level). #10440 is closer still to this project's shape: `tectonic_engine_spx2html` needs a patched `pinot`; the patch works locally, but "when the sub-crate is published... the patch directive does not get embedded in the published Cargo.toml artifact... downstream consumers installing the crate receive an unpatched version... builds fail because the patch adds required API functionality." That is structurally identical to `arti-wrapper` → patched `arti-client`/`tor-chanmgr`/`tor-guardmgr`, except in this project's case the unpatched behavior doesn't fail to *compile* (no new API surface is consumed at the type level) — it fails to *work correctly at runtime*, which is arguably worse because it's silent.

**What this means concretely for this repo.** Publishing `arti-wrapper` today, after fixing the version-field hygiene issue (§7), would **succeed** — `cargo publish -p arti-wrapper` would produce a crate whose manifest declares plain version dependencies on `arti-client = "0.43"`, `tor-chanmgr = "0.43"`, `tor-guardmgr = "0.43"` (no `[patch]`, stripped automatically). Anyone who `cargo add arti-wrapper` gets vanilla crates.io `arti-client` 0.43.x, `tor-chanmgr` 0.43.x, `tor-guardmgr` 0.43.x — **not** the six vendored, patched copies. Every fix in `vendor/README.md` silently disappears for that consumer: the Windows `saturating-time` infinite-loop hang (`vendor/README.md:17-25`), the unbounded bridge-descriptor fetch (`:32-36`), the `RwLock`-poisoning netdir bricking (`:37-59`), the `SQLITE_BUSY`/`SQLITE_LOCKED` fatal-bootstrap misclassification (`:61-84`), the zombie-channel `terminate_all_channels()` gap (`:86-123`), and the guard-readiness/recovery gaps in `tor-guardmgr`/`arti-client` (`:146-306`) all come back. For a Tor-network client — where a stuck bootstrap or a 100%-CPU hang on Windows is not a cosmetic bug — shipping that silently to `cargo add` users would be actively worse than not publishing at all.

**Is there a path around it?** Three real patterns exist in the wild (none of them free):
1. **Wait for upstream to accept the fixes**, then depend on a released arti version that no longer needs the patch. This removes the problem at the root but is on Tor Project's/Codeberg maintainers' timeline, not this project's (§2).
2. **Publish the vendored forks themselves under new crate names** (e.g. as this project already does its own vendoring under the *same* name via `path`, a public fork would need a different crates.io name — `tor-*` namespace collisions aside, that is also a courtesy issue, not just a technical one, towards the Tor Project). Then `arti-wrapper` would take a normal (non-patched, non-stripped) dependency on the fork crate, which *does* propagate to consumers correctly, at the cost of owning that fork's maintenance forever (re-diffing against every upstream arti release — a burden this project's own `docs/upstream/arti-vendor-integration-plan.md:361-389` already discusses for the *unpublished* vendoring it does today).
3. **Don't publish the arti-touching crates at all**, and publish only the 7 packages that never depend on the patched graph. This is free today (§5, §7 "phase 2").

None of these is a "just flip a switch" fix; that is the honest state of this blocker.

## 3. License compatibility

Confirmed against the live crates.io registry (not just this repo's vendored copies), via `https://crates.io/api/v1/crates/arti-client` and `https://crates.io/api/v1/crates/saturating-time`:

- **`arti-client`** (and by extension the whole Tor Project `tor-*` family vendored here — `tor-dirclient`, `tor-dirmgr`, `tor-chanmgr`, `tor-guardmgr`, `tor-circmgr`, all confirmed individually via each `vendor/*/Cargo.toml`'s own `license = "MIT OR Apache-2.0"` field): license **`MIT OR Apache-2.0`**, repository `https://gitlab.torproject.org/tpo/core/arti.git/`, currently at 0.46.0 upstream (this workspace pins/vendors 0.43.0 — three minor releases behind, a maintenance-burden data point for §2/§7, not a license issue).
- **`saturating-time`**: license **`MIT OR Apache-2.0`**, owned by Clara Engler (crates.io login `cvengler`), repository `https://codeberg.org/cve/saturating-time`, currently at 0.4.0 upstream (vendored copy is 0.3.0-based).
- **This workspace**: `license = "MIT OR Apache-2.0"` at `Cargo.toml:18`, inherited by every member via `license.workspace = true` (confirmed present in every `packages/*/Cargo.toml` and `apps/*/Cargo.toml` read for this report). `LICENSE-MIT` and `LICENSE-APACHE` both exist at the repo root.

**Verdict: fully compatible, no license blocker.** Both upstreams use the exact same dual-license as this project, so vendoring, patching, and (if ever pursued) republishing forks under either MIT or Apache-2.0 terms is permitted by the license text itself. The only non-legal consideration is courtesy/attribution if a fork is ever published under a new name (see §1, option 2) — not a blocker, just something to do properly (preserve upstream copyright/license notices, which the full-source vendoring under `vendor/` already does).

**What's missing for SDK-grade, across the board:**
- **No `examples/` directory anywhere** in `packages/*` (checked via `find … -iname examples`, none found) — every one of the above would benefit from at least one runnable example before a first publish.
- **No `#![warn(missing_docs)]`/`#![deny(missing_docs)]`** anywhere, and doc-comment density is uneven (`socks5-proto` at 18 lines for a 790-line file is the clear outlier; item-level doc coverage there needs a real pass).
- **`socks5-proto`'s `auth::AuthState` coupling** (above) is the one actual API-design issue worth fixing before publish, not just polish — either generalize to a trait or make the auth parameter fully optional/generic.
- **A single repo-root `README.md`** is what every crate's `readme.workspace = true` resolves to (Cargo resolves inherited `readme`/`license-file` relative to the *workspace* root, confirmed via the Cargo Book's workspace-inheritance reference — this is *not* a publish blocker, the file exists and packaging will succeed, but every crate's crates.io/docs.rs landing page would show the same whole-project SOCKS5-proxy README rather than crate-specific framing). Worth a short per-crate summary before publish, not required for it to work mechanically.
- **Version discipline**: every crate is `0.1.0` today. That's idiomatic for a first publish under semver (0.x.y permits breaking changes on a minor bump without technically violating semver), not a defect — but it does mean none of the API surface above has been deliberately reviewed as "this is the shape we're committing external consumers to."

## 6. `android-ffi` — confirmed out of scope

`packages/android-ffi/Cargo.toml:15-17`:
```toml
[lib]
name = "torsocks5"
crate-type = ["cdylib"]
```
`crate-type` is `cdylib` **only** — no `rlib`. This is not a style choice that happens to also work as a library; a cdylib-only crate produces a shared object (`libtorsocks5.so`) and does not emit the `.rlib`/metadata artifacts another Rust crate needs to `use` its types. Consistent with this, its public surface is three wildcard re-exports (`pub use jni_bridges::*; pub use jni_engine::*; pub use jni_verify::*`, `lib.rs:306-308`) meant to back JNI native-method symbols, not a Rust-facing API — the crate's 150-line top-of-file doc comment (`lib.rs:1-151`) is entirely a Java/Kotlin contract (`nativeStart`/`nativeStop`/`nativeGetStatus`, callback interface, status-string protocol), not Rust API documentation. `Cargo.toml` also pulls `jni = "0.21"` and, Android-only, `libc` via `[target.'cfg(target_os = "android")'.dependencies]` (`:37-43`).

**Conclusion: explicitly scoped out, not silently ignored.** `android-ffi` should never be a target of "publish as SDK." Its correct distribution channel is compiling the `.so` and shipping it through Android tooling (AAR/Maven or direct asset bundling), never `cargo add`. Publishing it to crates.io would be technically possible (crates.io doesn't forbid `cdylib`-only crates) but pointless — no Rust consumer could import anything from it, so it would serve no purpose an AAR wouldn't serve strictly better.

## 7. Practical blockers checklist

- **Missing `version` on every internal path dependency — the one hard, mechanical blocker.** Exhaustively grepped (`path = "\.\./` across every `packages/*/Cargo.toml` and `apps/*/Cargo.toml`): **26 occurrences, zero with a `version` field.** Full list: `apps/socks5-proxy/Cargo.toml:16-26` (9: `arti-wrapper`, `auth`, `bridge-fetcher`, `bridge-probe`, `bridge-store`, `bridge-verify-core`, `persist-lock`, `proxy-config`, `socks5-proto`); `packages/android-ffi/Cargo.toml:20-27` (8: `arti-wrapper`, `auth`, `proxy-config`, `socks5-proto`, `bridge-probe`, `bridge-fetcher`, `bridge-store`, `bridge-verify-core`); `packages/bridge-fetcher/Cargo.toml:16,18` (`arti-wrapper`, `bridge-probe`); `packages/bridge-store/Cargo.toml:17-18` (`bridge-probe`, `persist-lock`); `packages/proxy-config/Cargo.toml:20-21` (`bridge-probe`, `persist-lock`); `packages/socks5-proto/Cargo.toml:17` (`auth`); `packages/bridge-probe/Cargo.toml:17` (`persist-lock`); `packages/auth/Cargo.toml:23` (`persist-lock`). Cargo's own documented/confirmed behavior (`rust-lang/cargo` issue history) for this exact pattern: `cargo publish` errors with *"all dependencies must have a version specified when publishing… dependency `X` does not specify a version."* **Fix**: add `version = "0.1.0"` next to every `path = "…"`, e.g. `persist-lock = { path = "../persist-lock", version = "0.1.0" }`. Trivial, but currently 100% unaddressed across the whole workspace — this blocks *every* crate, including the 7 with no vendor-chain problem at all, and should be phase 1 regardless of which publishing path is chosen.
- **`description`/`license`/`repository`/`homepage`/`authors`/`keywords`/`categories`/`rust-version`**: present on every crate, all via `.workspace = true` inheritance from `Cargo.toml:16-25` (verified individually in every `packages/*/Cargo.toml` and `apps/*/Cargo.toml` read for this report — no overrides, no gaps). `readme.workspace = true` resolves against the *workspace root* `README.md` (Cargo's documented special-case for inherited `readme`/`license-file` paths, unlike `include`/`exclude` which stay package-relative) — that file exists (8366 bytes), so this mechanically works; the only downside is every crate's crates.io page shows the same whole-project README (cosmetic, §4).
- **No `build.rs` anywhere** in `packages/*` or `apps/*` (checked via `find … -iname build.rs`, none found) — no build-script portability/assumption risk.
- **`#[cfg(windows)]`/`#[cfg(unix)]`/`#[cfg(target_os = …)]` usage in `packages/*`** (full-workspace grep): confined to `bridge-verify-core/src/pt_reap.rs:349` (a `#[cfg(test)]`-gated unit test with a `#[cfg(not(windows))]` counterpart — not a compile hazard), `persist-lock/src/dir.rs:3,26` (a real `#[cfg(unix)]` `sync_parent_dir` with a documented `#[cfg(not(unix))]` no-op fallback at `dir.rs:31-35` — compiles and degrades gracefully everywhere; note this fallback is *already* what runs in this project's actual Windows deployment today, so it's an existing, intentional tradeoff, not a new one introduced by publishing), and `android-ffi` (expected, and out of scope per §6). **None of the SDK-candidate crates (`socks5-proto`, `persist-lock`, `bridge-probe`, `bridge-store`, `auth`, `proxy-config`) have a platform assumption that would surprise a Linux/macOS consumer.** The real platform-specific surface (`windows-service`, `windows-sys`, `[target.'cfg(windows)'.dependencies]` at `apps/socks5-proxy/Cargo.toml:60-68`; `daemonize` under `[target.'cfg(all(unix, not(target_os = "android")))'.dependencies]` at `:70-71`) is correctly isolated at the *application* level, not leaked into the library packages.
- **`dev-dependencies`**: none use `path =` anywhere in the workspace (all are versioned: `tempfile = "3"`, workspace `criterion`/`proptest`/`tokio`-with-features) — no external-consumer resolution risk there.
- **Version numbers**: everything is `0.1.0`. Fine for a first crates.io publish (idiomatic pre-1.0 semver, breaking changes ride on minor bumps) — not a blocker, just a signal that the public API hasn't yet been through a deliberate stability review (§4).
- **MSRV**: `rust-version = "1.89"` (`Cargo.toml:25`). Current stable as of this report is 1.98.1 (confirmed live) — a reasonably current but not bleeding-edge/unreleased requirement; not a blocker.
- **Minor, non-blocking cleanups noticed in passing**: the workspace `members` list has redundant entries — `packages/android-ffi` is listed explicitly *and* matched again by the `packages/*` glob (`Cargo.toml:4-5`); same for `apps/pt-helper` vs. `apps/*` (`:6-7`). Harmless (Cargo dedupes), but worth tidying if touching this file anyway. `rusqlite = { version = "0.39", features = ["backup"] }` is declared independently in three places (`android-ffi`, `bridge-verify-core`, `apps/socks5-proxy`) rather than once via `workspace.dependencies` — cosmetic only.

**Phase 2 — publish the 7 vendor-clean crates (~1-2 weeks, fully in this project's control).** In dependency order: `persist-lock` → `bridge-verify-core` → `auth`, `bridge-probe` → `socks5-proto`, `bridge-store`, `proxy-config`. **Phase 3 — send the upstream patches that already exist, and draft the next-best ones (weeks-to-months, partly outside this project's control).** Send `saturating-time` and the `tor-dirclient`+`tor-dirmgr` (fix 1/3) patches now via the channels already researched and written up in `docs/upstream/WHERE-TO-SEND.md` — zero additional engineering cost, only maintainer-response-time risk. In parallel, draft and send the `tor-chanmgr` pair (best ROI per this project's own integration-plan analysis, §2) and the two remaining plausible `tor-dirmgr` fixes (`shared_ref.rs`, `sqlite_error_kind`). Decide separately whether the `tor-guardmgr`/`arti-client` pair is worth drafting now or waiting to see whether phase-3's other landings already reduce the guard-exhaustion pressure that motivated it (per `arti-vendor-integration-plan.md:404-417`'s own sequencing argument).

**Phase 4 — publish the arti-touching crates (months out, gated on phase 3's outcome).** Once enough of the above lands in a released upstream `arti` version this project can adopt, re-evaluate the `[patch.crates-io]` list: if it shrinks to just `tor-circmgr` (which never leaves it, §2), that's an acceptable steady state — `arti-wrapper`/`bridge-fetcher` can then be published depending on stock crates.io `arti-client`/`tor-chanmgr`/`tor-guardmgr`/`tor-dirmgr`/`tor-dirclient`/`saturating-time`, with only `tor-circmgr`'s optional (default-off) bandwidth-floor behavior remaining as a documented local-only feature gap for published-crate consumers (who simply won't get that knob, which defaults to stock behavior anyway per `Cargo.toml:113-117`).
