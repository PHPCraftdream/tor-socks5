## TS4-01 — P2: таймаут входящего handshake не покрывает upstream setup

**Место:** [Upstream::connect:64–70](../apps/socks5-proxy/src/upstream.rs#L64-L70),
[ожидание метода:82–89](../apps/socks5-proxy/src/upstream.rs#L82-L89),
[handle_client](../apps/socks5-proxy/src/server.rs#L600).

30-секундный `HANDSHAKE_DEADLINE` ограничивает обмен с входящим клиентом.
После его завершения upstream-ветка вызывает `up.connect().await` без
внешнего бюджета. Внутри нет timeout для TCP connect, выбора метода,
RFC 1929 authentication и ответа CONNECT.

Контрпример: настроенный upstream принимает TCP и greeting, но больше
ничего не отправляет. Входящий клиент уже прошёл свой handshake; его
задача и permit остаются занятыми неограниченно. Достаточное число обычных
запросов при таком отказе upstream заполняет лимит соединений прокси.
Таймаут входящего клиента из первого раунда этот этап не ограничивает.

**Исправление:** единый deadline исходящего setup, включая DNS/TCP,
выбор метода, authentication и CONNECT reply. При истечении закрывать
upstream socket и возвращать ошибку клиенту; установленный relay имеет
отдельный жизненный цикл.

**Регрессия для исправления:** один permit, управляемый upstream, остановка
по очереди на method/auth/CONNECT reply. Каждая остановка заканчивается
по бюджету, permit освобождается; работающий relay продолжает передачу
после истечения времени, отведённого первоначальному setup.

## TS4-02 — P2: принимается NO_AUTH, которого не было в greeting

**Место:** [negotiate_method:74–98](../apps/socks5-proxy/src/upstream.rs#L74-L98).

При заданных credentials greeting содержит ровно один метод: `05 01 02`.
Однако ответ upstream `05 00` попадает в безусловное `M_NO_AUTH => Ok(())`.
Клиент продолжает CONNECT, хотя сервер выбрал метод вне предложенного набора.
Authentication, включённая конфигурацией, фактически пропускается.

Условие — некорректный или подменённый ответ upstream; обычный сервер,
выбирающий предложенный USER/PASS, эту ветку не вызывает. Правило выбора
из предложенных METHODS определено в
[RFC 1928, §3](https://www.rfc-editor.org/rfc/rfc1928.html#section-3).

**Исправление:** проверить, что выбран именно предложенный метод, до
перехода к соответствующему обмену. `0xFF` остаётся отказом, любой другой
непредложенный метод — ошибкой протокола.

**Регрессия для исправления:** при credentials ответ `05 00` даёт ошибку
и на upstream не отправляется CONNECT. `05 02` запускает authentication;
без credentials `05 00` работает штатно.

## TS4-03 — P2: probe не воспроизводит настройки WebTunnel

**Место:** [выбор target:101–125](../packages/bridge-probe/src/probe.rs#L101-L125),
[вызов probe:188–202](../packages/bridge-probe/src/probe.rs#L188-L202),
[TLS и Host:287–325](../packages/bridge-probe/src/probe.rs#L287-L325).

Для проверки передаются только адреса, host и URL. Параметр `servername`
теряется: SNI и HTTP Host всегда берутся из URL. Кроме того, probe всегда
запускает TLS, даже для `http://`. Транспорт WebTunnel допускает оба URL
scheme и использует `servername` для TLS/Host. Параметр `addr=hostname:port`,
который понимает транспорт, probe также отклоняет, требуя SocketAddr.

Работающий endpoint с HTTP URL либо отличающимся `servername` может успешно
устанавливать транспортное соединение и одновременно получать отрицательный
результат предварительной проверки. `Outcome::Unreachable` исключает его
из alive-пула и участвует в накоплении ошибок здоровья. Это расхождение
реализаций проверки и подключения, а не недоступность самого моста.

**Исправление:** использовать общий проверенный план target/SNI/Host/scheme
и одинаковые правила overrides. Проверка должна открывать соединение
с теми же существенными параметрами, что и будущий транспорт.

**Регрессия для исправления:** одна конфигурация проходит и probe, и
WebTunnel handshake: отдельно HTTP endpoint, отличный `servername`
и hostname в `addr`. Отрицательные результаты проверяются при реальном
нарушении сертификата/Upgrade, а не из-за потерянного параметра.

## TS4-04 — P2: первый ответ DoH ждёт всю волну запросов

**Место:** [race_doh_wave:401–452](../packages/bridge-probe/src/probe.rs#L401-L452),
[внешний DNS timeout:175–183](../packages/bridge-probe/src/probe.rs#L175-L183).

Первый пригодный ответ сохраняется в `answer`, но функция продолжает
`attempts.next().await` до завершения всех запросов. `answer.is_some()`
пропускает только обработку очередного результата, а не ожидание.
Один быстрый provider и три молчащих provider дают задержку всей волны
до 4-секундного timeout проигравших, даже если адрес уже получен.

Ожидание semaphore находится перед этим timeout. При очереди за permits
поздний проигравший запрос может задержать выдачу уже готового ответа
до внешнего 15-секундного DNS deadline. В таком случае caller получает
`Unmeasured`, хотя успешный ответ был доступен внутри отменённого future.
Документированное поведение «first successful answer wins» не выполняется
по времени возврата.

**Исправление:** возвращать первый пригодный ответ и отменять принадлежащие
волне проигравшие futures. Обновлять оценки по завершившимся запросам;
сбор статистики не должен удерживать готовое соединению значение.

**Регрессия для исправления:** быстрый успешный future и заблокированные
остальные, включая ожидание permit. Возврат происходит до освобождения
проигравших; принадлежащая вызову незавершённая работа после возврата отсутствует.

## TS4-05 — P2: периодическая запись уничтожает сохранённый DNS fallback

**Место:** [load/save:379–415](../packages/bridge-probe/src/dns.rs#L379-L415),
[disk fallback:422–431](../packages/bridge-probe/src/dns.rs#L422-L431),
[его использование](../packages/bridge-probe/src/probe.rs#L496),
[периодическая запись Android](../packages/android-ffi/src/engine_bootstrap.rs#L427).

Загрузка файла помещает ответы в `disk_fallback_store`. `save_persisted_dns_cache`
сериализует только положительные записи другой структуры, `doh_cache`.
Успешное использование disk fallback не переносит его в doh_cache.

Контрпример: новый процесс загрузил корректный файл, DoH на текущей сети
недоступен, соединения используют сохранённые IP. На очередном tick
Android сохраняет пустой doh_cache поверх этого файла. В текущем процессе
ответ ещё доступен в disk_fallback_store, но после следующего перезапуска
процесса единственный пригодный fallback исчезает. Частично заполненный
doh_cache аналогично теряет остальные ещё допустимые сохранённые ответы.

**Исправление:** сохранять объединение актуальных результатов и ещё не
истёкших fallback-записей с определённой политикой замены. Сохранять их
исходный возраст; повторная запись не превращает старый ответ в свежий.

**Регрессия для исправления:** load → использование только disk fallback →
save → очистка состояния процесса → load. Допустимая запись сохраняется;
действительно истёкшая удаляется. Проверить также частичное обновление кеша.

## TS4-06 — P2: timestamp из будущего закрепляет DNS hint

**Место:** [parse_dns_hint_line:475–492](../packages/bridge-probe/src/dns.rs#L475-L492),
[merge:356–365](../packages/bridge-probe/src/dns.rs#L356-L365),
[возраст fallback:422–431](../packages/bridge-probe/src/dns.rs#L422-L431),
[scope-фильтр импорта](../packages/proxy-config/src/lib.rs#L620).

Timestamp принимается как произвольный `u64`. В merge побеждает большее
значение, а возраст вычисляется через `now.saturating_sub(timestamp)`.
Для будущего времени возраст равен нулю; значение вроде `u64::MAX`
не истечёт по 24-часовому пределу и не уступит следующему корректному hint
с реальным текущим временем.

Проверка соответствия hostname импортируемым мостам не проверяет время.
Некорректные часы устройства или специально сформированный QR hint для
разрешённого hostname могут поэтому закрепить нерабочий адрес. Проявление
касается fallback при недоступном DoH; свежий успешный DoH-ответ имеет
свой отдельный путь и из этого пункта обход TLS-проверки не следует.

**Исправление:** проверять допустимое отклонение будущего времени при
импорте, загрузке и merge. Невалидный timestamp не должен участвовать
в выборе «самой новой» записи. Политику clock skew задать явно.

**Регрессия для исправления:** hint существенно из будущего, затем
корректная запись того же hostname; некорректная запись не блокирует замену.
Проверить крайний u64, небольшое допустимое отклонение и истечение TTL
на управляемых часах.

## TS4-07 — P2: адрес TLS и HTTP authority используют одно представление

**Место:** [UrlTarget:20–38](../packages/bridge-fetcher/src/url_parse.rs#L20-L38),
[TLS и построение запроса:296–312](../packages/bridge-fetcher/src/http.rs#L296-L312),
[Host:77–88](../packages/bridge-fetcher/src/http.rs#L77-L88).

Для `https://example.com:8443/list` TCP подключается к 8443, но request
содержит `Host: example.com`: port вообще не передаётся в build_get_request.
Endpoint, маршрутизирующий по полной authority, получает запрос к другой
authority. Правила Host определены в
[RFC 9110, §7.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-7.2).

Для IPv6 URL `host_str()` содержит скобки. Это представление без изменения
идёт в connector и `ServerName::try_from`; `"[::1]"` не является корректным
IP-значением для TLS ServerName. Даже если connector сумел установить TCP,
этот TLS-шаг отклонит имя. При этом скобки нужны для IPv6 в HTTP authority.

**Исправление:** различать dial/TLS host и wire authority. IP для socket/TLS
передавать без скобок, Host формировать со скобками IPv6 и нужным port.
Нормализованный origin для политики credentials должен остаться согласованным
с тем же URL-разбором.

**Регрессия для исправления:** HTTPS с нестандартным port и IPv6 literal;
проверить фактический Host и TLS ServerName, а не только поля UrlTarget.
Редирект между port по-прежнему считается переходом на другой origin.

## TS4-08 — P2: три IPv4-ответа вытесняют все IPv6-кандидаты

**Место:** [MAX_PROBE_ADDRS и order_candidates:375–395](../packages/bridge-probe/src/probe.rs#L375-L395).

Адреса сначала сортируются так, чтобы все IPv4 шли первыми, затем берутся
первые три. При ответе `A1, A2, A3, AAAA1` ни один IPv6 не попадёт
в результат. Обещание пробовать оба семейства не выполняется, когда
IPv4-адресов достаточно для заполнения лимита.

Контрпример: все три A немедленно отказывают в подключении, AAAA пригоден.
Мост либо HTTPS-источник объявляется недоступным без попытки IPv6,
хотя DNS вернул рабочий адрес. Тесты отдельно проверяют порядок двух
семейств и ограничение списка IPv4, поэтому эту комбинацию не покрывают.

**Исправление:** распределять ограниченный бюджет между присутствующими
семействами, сохраняя предпочтение IPv4, порядок DNS внутри семейства
и дедупликацию. При лимите ≥2 каждое присутствующее семейство должно
получать хотя бы одну попытку.

**Регрессия для исправления:** три и более A вместе с AAAA; результат
не превышает лимит и содержит оба семейства. Управляемый dial подтверждает
переход к IPv6 после немедленных IPv4-отказов.

## TS4-09 — P3: глубокая COW-копия всё ещё выполняется на async worker

**Место:** [actor:216–219](../apps/socks5-proxy/src/bridge_store_writer.rs#L216-L219),
[мутация:342–348](../apps/socks5-proxy/src/bridge_store_writer.rs#L342-L348),
[publisher](../apps/socks5-proxy/src/bridge_store_writer.rs#L465),
[BridgeStore](../packages/bridge-store/src/lib.rs#L194).

В TS3-09 исправлена стоимость получения publish snapshot: clone Arc дешёв.
Однако publisher удерживает сильную ссылку, и первая мутация actor во время
публикации вызывает `Arc::make_mut`. При нескольких сильных ссылках этот
метод клонирует внутреннее значение, как описано в
[контракте Arc::make_mut](https://doc.rust-lang.org/std/sync/struct.Arc.html#method.make_mut).
BridgeStore по-прежнему содержит глубоко клонируемый BTreeMap со строками.

Итак, копия O(S) переместилась с публикации на первую конкурентную мутацию
того же async actor. Она задерживает ack и worker; пик включает два
снимка размера O(S). Это происходит при разделяемом снимке, а не на каждой
мутации. Здесь повторно отмечена именно оставшаяся часть TS3-09.

**Исправление:** вынести владение тяжело мутируемым состоянием на отдельного
синхронного владельца либо использовать структурное разделение данных,
которое не копирует весь store ради одной записи. Сохранить порядок
мутаций, retry и подтверждение их приёма.

**Проверка для исправления:** удерживаемый publisher и следующая мутация;
инструментация места выполнения Clone подтверждает отсутствие глубокой
копии на async worker. Время и число аллокаций измерить отдельно.

## TS4-10 — P3: chunk metadata читаются с лишними аллокациями

**Место:** [ChunkedReader:35–90](../packages/bridge-fetcher/src/http/framing.rs#L35-L90),
[цикл chunks](../packages/bridge-fetcher/src/http/framing.rs#L107).

`read_line` создаёт новый Vec и запрашивает у AsyncRead по одному байту.
Он вызывается для каждой строки размера chunk и trailer. При K мелких
chunks это K короткоживущих буферов и число вызовов read/poll,
пропорциональное числу байтов framing. TLS может обслуживать их из своего
буфера: утверждать, что каждый вызов обязательно делает syscall, нельзя.

Декодирование остаётся линейным, но дробление одного тела на множество
chunks резко увеличивает постоянные расходы. Само корректное удаление
chunked framing из TS3-07 этим наблюдением не оспаривается.

**Исправление:** буферизованное чтение с поиском CRLF в уже полученном
блоке и переиспользованием ограниченного scratch. Сохранить пределы
метаданных, decoded body и корректность при произвольных границах чтения.

**Проверка для исправления:** одинаковое тело с крупными и мелкими chunks,
CRLF на границе буфера, extensions и trailers. Считать allocations и
вызовы нижележащего reader; равенство результата не доказывает снижение затрат.

## Проверка и границы выводов

Находки основаны на статическом разборе текущих веток и callers.
Регрессии выше предложены для исправлений, но в этом раунде не запускались.
Сборки, runtime/network проверки, нагрузочные тесты и измерения ускорения
не проводились. Коммит содержит отчёт, без изменений кода или версий.

Для документа проверены существование исходных ссылок и строк,
согласованность ID/приоритетов, отсутствие частных путей и
`git diff --check`. Исходные находки и критерии проверок относятся
к указанному в начале коммиту.
