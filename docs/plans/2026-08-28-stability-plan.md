# План повышения стабильности коннекта (desktop CLI)

Дата: 2026-08-28. Основание: живой разбор продового лога `start-12.err`
(12:57–14:53), health-store `tor-socks5.alive-bridges.log`, код
`tor_watchdog.rs` / `fetch_merge.rs` / `bridge-store` / `android-ffi/engine.rs`,
документ `docs/upstream/guard-exhaustion-watchdog-spiral.md`.

---

## 1. Диагноз: почему нестабильно

Наблюдённая картина одного рана (боевой лог, не гипотезы):

- 12:57–14:16 — простой без клиентского трафика; за это время каналы
  зомбируются (Wi-Fi-события Netwtw10 в 14:04/14:07). Трафик вернулся в
  14:16 → stale-watchdog за ~60 с сделал `terminate_all_channels` → успехи
  через 19 секунд. **Этот механизм работает.**
- 14:17–14:53 — под нагрузкой Telegram (100–320 conn/мин) успехи идут
  вспышками (20/42/28/116 в минуту), между ними окна `established=0` по
  10–20 минут. В этих окнах watchdog **семь раз отказался лечить**
  (`declining: RemoteNetworkTimeout, not TorNetworkTimeout`), хотя
  единственный выполненный heal доказанно чинил ровно такое состояние.
- Весь ран, каждые ~5 минут, `spawn_bridge_failover_watchdog` сигналит
  arti «guard failure» по одному и тому же набору из 10 мостов (по 7–12 раз
  каждый), первый залп — через 45 с после бута, на основании `cfails` из
  стора **от 25 августа**. В окнах guard-истощения «Rejected 10–15/30 as
  down» — заметная часть этих down — наша же работа.
- В топ-30 активного пула сидит `obfs4 8.8.8.8:443 ...` — Google DNS,
  мусор из скрейпленного источника, с идеальной TCP-репутацией
  (`fails=0 seen=553`) и 10 полученными failover-сигналами.
- У **всех 115 мостов** `evseen=0 evok=- chseen=0 chok=-`: end-to-end и
  канальная верификация из `31240c7` подключены только в
  `android-ffi/engine.rs`; CLI их не пишет и не читает. Ранжирование
  «healthiest» — по-прежнему чисто TCP.

Три дефекта усиливают друг друга:

1. **Admission по голому TCP** (`drain_pool`, `fetch_merge.rs:157-190`) —
   мусор попадает в боевой конфиг и занимает guard-слоты.
2. **Failover без реабилитации** — сигнал уводит мост из ротации → через
   него не строятся circuits → `cfails` не сбрасывается (сброс только по
   успешному circuit, `arti_observability.rs:194`) → кулдаун истёк →
   сигнал снова. Вечная карусель наказаний, кормимая в т.ч. мусором из п.1.
3. **Гейт heal перекалиброван** (`should_decline_rebuild`,
   `tor_watchdog.rs:395`). Он писался, когда «лечение» = rebuild в холодный
   слот (цена ошибки — 12 минут дескрипторного голода, июльский инцидент).
   Сегодня лечение = `terminate_all_channels` на живом клиенте с тёплым
   кэшем + канарейка: цена ошибочного heal — секунды. А цена пропущенного —
   десятки минут отказа. Гейт же по-прежнему запрещает heal при доминанте
   `RemoteNetworkTimeout`, хотя зомби-канал после смены сети даёт **именно
   её** (BEGIN в пустоту по уже построенному circuit) — сам июльский
   документ признаёт неразличимость этих случаев (приложение, п.1).

Первопричина умирания потоков (Wi-Fi / DPI flow-kill / rate-limit на
стороне мостов — 923 RST на obfs4-хендшейках за ран) по логу до конца не
атрибутируется. **Это не блокер**: план чинит устойчивость системы к
умирающим потокам, что полезно при любой из трёх причин.

## 2. Принципы (чтобы не наплодить новых спиралей)

- **Admission важнее наказания.** Не пускать мусор в пул дешевле, чем
  вечно его карать.
- **У каждого наказания должна быть реабилитация.** Механизм без пути
  назад со временем наказывает всё.
- **Действовать только по свежим уликам.** Сигналы по `cfails` трёхдневной
  давности через 45 с после бута — не улики.
- **Цена действия изменилась — перекалибровать гейт.** Heal больше не
  опасен; держать его запертым в тотальном отказе — вредно.
- **У каждого актуатора — бюджет и backoff.** Метроном «каждые 5 минут
  навсегда» недопустим ни для одного механизма.

## 3. Фазы работ

Каждая фаза — независимо поставляемая, со своими тестами и отдельным
коммитом. Порядок = убывание (отдача / риск).

### Фаза 0 — операционная, без кода: вычистить мусор

- Удалить `obfs4 8.8.8.8:443 0353110423...` из
  `C:\Users\Computer\Desktop\resocks5\tor-socks5\tor-socks5.ktav`
  (`bridges.lines`) и из `tor-socks5.candidates.log` (если есть).
- Перезапуск сервиса. Бекап перед изменением (стандартная практика).
- Примечание: до Фазы 2 мусор может вернуться через `drain_pool` из
  свежескрейпленных источников — это приемлемо на несколько дней.

### Фаза 1 — `tor_watchdog.rs`: разблокировать heal, остановить метроном

**1a. Эскалация через гейт (heal override).**

В цикле `spawn_tor_watchdog`: счётчик `gated_ticks`. Когда условия 1–3
выполнены, но `should_decline_rebuild` вернул `true` — инкремент; на любом
успехе (`last_success` сдвинулся) или выполненном heal — сброс. При
`gated_ticks >= 2` (≈90 с реального тотального отказа) — **лечить несмотря
на сигнатуру**, с отдельным WARN «signature override: total outage
persists». Существующие ограничители остаются: кулдаун 300 с,
`consecutive_failures >= 3` → 30-минутный backoff, канарейка
`verify_usable`.

Почему это безопасно против июльской спирали: (а) тот кейс — 8 попыток за
218 с — сегодня вообще не проходит `MIN_ATTEMPTS_TO_TRIGGER=3` на тик;
(б) само действие сменилось с «rebuild в холодный слот» на дешёвый
in-place terminate; (в) override требует ≥2 последовательных полностью
провальных тиков, а не одного плохого окна.

Тесты: юнит на логику `gated_ticks` (вынести решение в чистую функцию
`should_override_decline(gated_ticks, ...)` рядом с
`should_decline_rebuild`), кейсы: июльская сигнатура не эскалирует
(мало попыток), сегодняшняя (2 тика × 100+ remote_timeout, 0 успехов)
эскалирует, успех сбрасывает счётчик.

**1b. Failover: свежесть улик + бюджет сигналов.**

В `spawn_bridge_failover_watchdog`:
- **Свежесть**: сигналить только если `last_circuit_observation` (`cobs`)
  моста новее старта процесса (передать `Instant`/`SystemTime` старта в
  задачу). Улики прошлых ранов — не основание выбивать гварда у свежего
  клиента. (`Health` в `bridge_warmer::candidates_with_health` придётся
  расширить полем `cobs` — сейчас он его не отдаёт; поле в сторе есть.)
- **Бюджет**: не более 3 сигналов на мост за жизнь процесса. После
  третьего — один INFO «giving up on signalling <bridge>» и молчание:
  либо мост мёртв и его снимет прунинг/верификация (Фаза 2), либо arti
  сам разберётся.

Тесты: чистая функция-предикат (`should_signal_failover` уже вынесен —
расширить сигнатуру или добавить обёртку с `cobs`/бюджетом), кейсы:
старый `cobs` — не сигналим, бюджет исчерпан — не сигналим, свежий
`cobs` + бюджет есть — прежняя логика.

### Фаза 2 — реальная верификация мостов в CLI

**2a. Admission через канал, не через TCP.**

`drain_pool` (`fetch_merge.rs`): после успешного TCP-probe кандидата —
дополнительно `tor.warm_bridge(&bridge)` (канал = obfs4 + Tor link
handshake; 8.8.8.8 отваливается мгновенно). Только успешный канал →
promotion в `bridges.lines`. Плумбинг: передать `Option<&TorTunnel>` из
maintenance-цикла (`server.rs`); при `None` (cold-start rescue, Tor ещё
нет) — прежний TCP-only критерий, это осознанный компромисс холодного
старта.

**2b. Записывать канальные результаты в стор.**

`bridge_warmer` при успешном/провальном прогреве и `drain_pool` при
admission-проверке — вызывать `note_channel_success_at` /
соответствующий failure-метод стора (сверить точные имена по
`packages/bridge-store/src/lib.rs`; поля `chseen`/`chok` уже есть).
Сейчас в CLI **ни одного вызова** `note_channel_success` нет.

**2c. Портировать периодическую circuit-верификацию из android-ffi.**

Источник: `packages/android-ffi/src/engine.rs` (~1083–1265, 1821–1850):
цикл берёт `BridgeStore::needing_circuit_verification(max_age, limit)`
(старейшие/непроверенные первыми), прогоняет реальную проверку через
конкретный мост, на успех — `note_circuit_verified_at`. Перед портом
прочитать реализацию точно (какой механизм проверки, какие таймауты,
как интегрировано с maintenance-тиком) — не изобретать заново.
Важно при порте: убедиться, что успешная верификация **также сбрасывает
`cfails`** (`note_circuit_success_at`) — это и есть путь реабилитации
для Фазы 1b; если в сторе `note_circuit_verified_at` этого не делает —
звать оба метода.

**2d. Ранжирование.** Проверить `healthiest_bridges`: учитывает ли оно
`evok`/`chok` (Android добавлял `verified_count`). Если нет — верифи-
цированные мосты должны ранжеваться выше чисто-TCP-живых; мусор без
единого канала — в хвост (и под прунинг по существующим правилам).

Тесты: admission-функция с инъецируемым «проверятелем канала» (без сети),
кейсы: TCP-ok+канал-fail — не промоутится, TCP-ok+канал-ok — промоутится,
cold-start без Tor — TCP-only; для 2c — портировать и адаптировать
существующие тесты engine.rs.

### Фаза 3 — известный баг транспортного fallback

`tor_setup.rs` (`build_tor_settings`): в ветке «active pool was
unreachable» retry идёт по `parsed_bridges` (все транспорты) вместо
`preferred_bridges` — утечка через транспортное предпочтение, которую
пользователь явно отверг; upstream починил эквивалент в `82a3d76`.
Замена одной переменной + тест на «webtunnel-предпочтение не деградирует
в obfs4 при недоступном активном срезе». Известен с `c2069e8`.

### Фаза 4 — позже, по результатам наблюдения (не делать сейчас)

- **Проактивный heal по событию смены сети** (Windows
  `NetworkListManager`/`NotifyAddrChange` → `terminate_all_channels`
  сразу, не ждать stale-окна). Настоящее лечение первопричины
  зомби-каналов; средний объём, делать после того как Фазы 1–2 покажут
  эффект.
- **Снизить агрессию проб/прогрева**, если 923 RST/ран — это
  rate-limiting мостов на нашу частоту переподключений (наблюдать после
  Фаз 1–2: churn упадёт сам — RST'ы должны уйти).
- **Телеметрия разнообразия назначений** в классификаторе отказов
  (отличать «один DC молчит» от «всё молчит» напрямую, а не через
  косвенный `gated_ticks`).

## 5. Риски и ограничители

- **Override гейта слишком агрессивен** → heal-churn при истинно
  заблокированной сети. Ограничители: кулдаун 300 с, backoff 30 мин после
  3 провалов, канарейка. Хуже сегодняшнего (перманентный отказ) стать не
  может.
- **`warm_bridge` в admission** добавляет нагрузку на прогрев по кандидату
  на промоушен: батч уже ограничен (`max_attempts`), канальная проверка
  только для TCP-живых — рост умеренный.
- **Порт 2c затрагивает семантику стора, общую с Android** — стор не
  менять поведенчески; всё новое — на стороне CLI-вызовов. Если для
  реабилитации нужен сброс `cfails` — добавлять вызовом существующего
  `note_circuit_success_at`, не правкой стора.
- **Честная неопределённость**: если первопричина — DPI flow-kill, Фазы
  1–2 сократят время восстановления, но не устранят сами обрывы;
  структурный ответ на DPI — webtunnel-пул (отдельная, уже отложенная
  тема: скрейпленный webtunnel почти весь сожжён, см.
  `docs/censorship-findings.md`).
