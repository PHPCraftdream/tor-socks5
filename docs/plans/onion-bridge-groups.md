# Группы мостов для onion-сервисов

- **Дата:** 2026-11-20
- **Статус:** влито в main (PR #153, CI зелёный: 1046 и 1049 тестов на двух ОС). Живой запуск старта группы на реальных мостах сделан один раз (раздел 8); отказ моста, замена и пересоздание клиента вживую не проверялись; ревью после влития нашло пробелы в надёжности (раздел 6).
- **Запрос.** Задавать количество мостов на сервис ради надёжности; в пределе — один конечный сервис на нескольких адресах, у каждого свои мосты.
- **Выбор владельца.** Группы: `bridge_group` + `bridges: N` на записи сервиса.

## 1. Почему нужен отдельный клиент

Arti не знает понятия «мосты этого сервиса»: набор guards, пул onion-цепей и состояние принадлежат одному `TorClient`. Поэтому все сервисы процесса идут через один мост (первый пригодный из первичных guards), а `tor.guard_spread` (1..3) делит цепи между 2–3 мостами сразу для всех сервисов. Свой набор мостов у сервиса возможен только через свой `TorClient` со своим состоянием guards.

В коде уже есть прецедент: одноразовые клиенты проверки моста (`verify_bridge_reachable`) берут свой `state_dir` и общий `cache_dir` процессного клиента, и консенсус не скачивается заново.

## 2. Что сделано

- **Конфиг** (`packages/proxy-config`, файл сервисов): `bridge_group` (`a-z 0-9 _ -`, до 25 байт; имя становится каталогом, поэтому только нижний регистр) и `bridges` (1..=8, по умолчанию 1; только вместе с `bridge_group`). Включённые сервисы одной группы обязаны указывать одинаковое `bridges`. Без `bridge_group` сервис работает как раньше.
- **Раздача мостов** (`apps/sdk/crates/server/src/onion/groups.rs`): рабочий список процесса сортируется по строке моста, группы идут в порядке имени, каждая получает свой непрерывный срез; при нехватке срезы заворачиваются и пересекаются (предупреждение), при `bridges` больше списка группа получает весь список (предупреждение). Тот же список даёт ту же раздачу при каждом запуске.
- **Клиент группы:** `Settings` процессного клиента, но `bridges` группы, `state_dir = <arti base>/group-<имя>`, `cache_dir` общий с процессным клиентом, `guard_spread = min(bridges, 3)`. Без мостов клиент не создаётся (клиент без мостов вышел бы в Tor напрямую).
- **Хостинг:** на группу свой `TorHandle` и свой `OnionHost` со своим keystore (`group-<имя>/state/keystore`) и своей блокировкой; сервисы без группы идут через процессный клиент, как раньше. Если все сервисы в группах, супервизор сам держит блокировку keystore процессного клиента, чтобы `onion new`/`remove` по-прежнему отказывали при работающем сервере.
- **Обслуживание группы (задача #563):** у группы собственное обслуживание, под тем же переключателем `[watchdog]` процесса (`enabled` и `check_interval_secs`) и в span `bridge_group{group=…}`. При выключенном обслуживании группа работает на наборе, назначенном при старте: ни заявок мостов, ни пересозданий нет.
  - *Заявка на мосты перед каждой попыткой.* Набор мостов группы пересчитывается из рабочего списка процесса (мосты, с которыми сейчас работает процессный клиент — `TorHandle::active_bridges`) **перед каждой** попыткой бутстрапа, начальной и повторной, и на каждом тике обслуживания. Группа, которая ещё ни разу не поднялась, поэтому тоже получает замену, как только в рабочем списке появляется свободный мост; на мёртвом назначенном мосте она не залипает. Мост группы, которого в списке нет, считается мёртвым; на его место берётся свободный мост рабочего списка в порядке строки моста, кроме занятых другой группой (реестр `GroupBridges` в памяти процесса). Выбор и запись в реестр идут под одним захватом блокировки, поэтому две группы не могут получить один и тот же свободный мост. Замена частичная: сколько есть свободных, столько мёртвых и заменяется, остальные остаются в наборе (могут ожить), поэтому число мостов группы не меняется ни вверх, ни вниз, а нехватка пишется `warn`.
  - *Владение мостом на время замены.* У живого клиента замена идёт в два шага: `reserve` под одним захватом блокировки выбирает свободные мосты и записывает группу как держащую старый и новый набор одновременно (поэтому соседняя группа не заберёт мост, на котором клиент ещё работает), затем `TorTunnel::reconfigure_bridges`; при успехе `commit` отпускает старые мосты, при отказе клиента `rollback` возвращает зарезервированные в пул и оставляет группе её прежний набор. Реестр поэтому равен фактическому набору клиента, а на время переключения — его надмножеству. Правило «один мост — одна группа» действует только на замене: стартовая раздача при нехватке рабочего списка заворачивает срезы, и один мост может достаться двум группам (каждая пишет `warn`); реестр хранит такое пересечение как есть, замена его не создаёт и не разрывает — общий мост считается занятым обеими группами, пока его не отпустит последняя. Когда группа останавливается насовсем (токен или исчерпанный бюджет пересозданий), её мосты освобождаются (`release`) для соседей. В `.bridges.ktav`, bridge-store и слоты процесса группа не пишет.
  - *Пересоздание зависшего клиента.* Группа следит за статусом хостинга (`OnionHostStatus`). Если ни один её сервис не `Running`/`DegradedReachable` дольше `watchdog.stale_after_secs` (клиенту, который ни разу не дошёл до `Running`, даётся окно старта 600 с, оно удваивается с каждым пересозданием до 1800 с), клиент пересоздаётся: задача обслуживания и хостинг останавливаются, и остановка **дожидается факта завершения** (при нужде — abort, после которого ожидание продолжается с предупреждениями), только затем клиент отдаётся из слота, читаются мосты для следующего поколения и начинается новый бутстрап. Если все сервисы в `Failed`/`Stopped`, решает типизированная причина: исчерпанное ожидание адреса (`ServiceFailure::AddressUnavailable`) даёт группе до двух дополнительных клиентов (`MAX_FAILED_RESTARTS`), любая другая причина (ключи, конфигурация, keystore) считается неизлечимой и группа останавливается сразу. Ошибки конфигурации самого клиента группы (pre-прокси, отсутствие `state_dir`) дают один `error` и останавливают группу, а не уходят в повтор. Отмена токеном сервера останавливает и обслуживание, и хостинг.
- **Логи:** строки группы идут в span `bridge_group{group=<имя>}`, строки сервиса несут `nickname`.
- **CLI:** `onion new` и `onion import` принимают `--bridge-group NAME [--bridges N]` и пишут поля в запись сервиса; значения проверяются теми же правилами, что и при чтении файла (одна общая проверка `check_group_args` в `packages/proxy-config`: имя группы, `bridges` только с группой, диапазон 1..=8), до создания ключа и записи в файл. `--force` меняет только идентичность: группа и её `bridges` остаются, если флаги не задают новые.

## 3. Критерии приёмки

1. Конфиг без новых полей читается и пишется как раньше; новые поля не появляются в файле, пока не заданы.
2. Неверные значения отвергаются с путём `services[i].…`: `bridges` без группы, `bridges` вне 1..=8, имя группы с верхним регистром/пробелом/точкой/длиннее 25, разное `bridges` у включённых сервисов группы.
3. Раздача: группы получают непересекающиеся мосты, пока хватает списка; раздача не зависит от порядка входного списка; нехватка списка не падает, а предупреждает.
4. Клиент группы: свои `state_dir`/keystore, общий кэш, только мосты группы, отказ без мостов.
5. `cargo check`, `clippy -D warnings`, `fmt`, структурные линты чистые; тесты зелёные в CI.

## 4. Не-цели

- Собственная проверка живости мостов группы и запрос новых мостов: группа следует рабочему списку процесса и своих проб не делает.
- Пересоздание клиента группы без перезапуска хостинга: при пересоздании сервисы группы публикуются заново (адрес и ключ те же), на время публикации они недоступны.
- Подключение к группе процессных `spawn_tor_watchdog` и `spawn_bridge_failover_watchdog`: первый по счётчикам попыток и успехов `connect` закрывает каналы живого клиента на месте, второй по здоровью мостов из bridge-store процесса сигналит guard manager. Счётчики `TorHealth` заполняет SOCKS5-путь процесса и рабочая проба его же обслуживания мостов (`apps/sdk/crates/runtime/src/bridges/bridge_maintenance.rs:597` — `record_success` после подтверждённой пробы; `:678` — тот же вызов в юнит-тесте, не в работе), то есть они описывают работу процессного клиента; onion-хостинг группы их не заполняет, и первый watchdog у клиента группы молчал бы. Пороги второго рассчитаны на большой пул, а у группы 1–3 моста и уже есть более решительная мера — замена моста по рабочему списку и пересоздание клиента по статусу хостинга. Подробности и цена подключения — раздел 6, пункт 2.
- Разный `circuit_hops` у групп (остаётся одно значение на процесс).
- Android (там onion-хостинг по умолчанию выключен).

## 5. Риски и что не проверено

- **Не измерено вживую:** поведение при отказе одного моста группы, замена моста, пересоздание клиента, долгая работа. Старт группы на реальных мостах измерен один раз (раздел 8). Для остального нужен второй прогон с разрешения владельца (нагрузка на мосты, задача #565).
- **Общий кэш каталога.** Клиент группы читает кэш процессного клиента (второй писатель блокируется, группа работает в режиме чтения). Старт подтверждён вживую (раздел 8): клиент группы поднялся за секунды без своей загрузки консенсуса, каталог группы занял 12 КБ при общем кэше 10 МБ; для долгоживущего клиента (устаревание консенсуса, обновление общего кэша) не проверено. Если консенсус в кэше устареет, пока процессный клиент не обновил его, клиент группы ждёт обновления.
- **Срок попытки отменяет ожидание, но не фоновые задачи Arti.** После обрыва попытки по сроку загрузка каталога, уже запущенная отдельной задачей, может ещё держать менеджер и транспорт (vendor/tor-dirmgr/src/bootstrap.rs), и следующая попытка начнётся поверх неё. Установлено чтением кода, не наблюдалось; проверить в живой проверке (шаг 1).
- **Замена мостов и пересоздание клиента группы не проверены вживую.** Признак «мост мёртв» — его отсутствие в рабочем списке процесса, а это набор конфигурации, не отдельный вердикт о мосте: процесс может сохранить набор, пока его маршрут ещё работает, и тогда мёртвый мост у группы не заменится. Обратная сторона: мост, снятый с процесса по другой причине (выбран другой пул), у группы тоже заменяется — безопасно (замена из рабочего списка, размер не меняется), но лишние переключения. Частичная замена держит в наборе мёртвые мосты, которых не на что менять, поэтому живой пул группы может быть меньше её `bridges`, пока свободных нет. Если рабочий список процесса обновился целиком, все группы захотят новых мостов в один тик; свободных хватит не всем, остальные получат `warn` и попробуют на следующем тике, то есть смена пула у групп растягивается на несколько `check_interval_secs`.
- **Пересоздание клиента группы в том же `state_dir` может упереться в блокировку состояния arti,** если прежний клиент ещё держат живые соединения или дети PT. Задача обслуживания и хостинг к этому моменту уже остановлены и дождались завершения, но in-flight соединения живого клиента удержать блокировку всё равно могут: тогда новый бутстрап повторяется с паузой (`bootstrap_until_ready`) и группа стоит, пока блокировка не освободится. Не хуже прежнего «стоит до перезапуска процесса», но и не лучше. Хостинг при пересоздании тоже перезапускается, так что сервисы недоступны, пока дескриптор не опубликуется снова.
- **Цена:** на группу один PT-процесс, свой набор соединений и бутстрап. 30 групп по одному сервису — тяжело; предпочтительны группы из нескольких сервисов.
- **Анонимность:** мосты группы видят только трафик группы (лучше для разделения), но суммарно больше мостов видят IP сервера.
- **Аварийная остановка не штатная.** Если общий бюджет остановки сервера истечёт (`PRODUCER_JOIN_TIMEOUT`, 120 с в `apps/sdk/crates/server/src/server/server.rs`), владелец производителей не дождётся задачи группы и оборвёт её (`producer_owner.abort()`), а вместе с ней — по `AbortOnDropHandle` — и её производителя (`apps/sdk/crates/server/src/onion/service.rs`). Тогда дочерние задачи поколения не присоединяются, `drain` клиента не выполняется и `release` мостов может не пройти вовсе: порядка «задачи → освобождение → чтение реестра» в этом пути нет. Последствий для следующего запуска нет — реестр живёт только в памяти процесса и умирает вместе с ним, — но это не штатная отмена, и полагаться на него как на остановку нельзя.

## 6. Ревью после влития (2026-11-20)

Цель запроса — надёжность выше. Код делает разделение по мостам; ревью нашло четыре места, где группа была слабее процессного клиента. Пункты 1–3 сделаны задачами #561 и #563 — но не «закрыты»: у пунктов 2–3 остаются ограничения (а)–(д), часть из них требует правок runtime и вынесена в шаг 7 раздела 7; пункт 4 остаётся за шагом 4:

1. **Повтор бутстрапа — сделано (задача #561).** `run_group` больше не сдаётся после одной ошибки: попытки идут, пока не сработает токен отмены сервера. Срок одной попытки — 120 с (`BOOTSTRAP_ATTEMPT_LIMIT`), пауза после неудачи — 5 с с удвоением до потолка 300 с (`BOOTSTRAP_FIRST_DELAY`, `BOOTSTRAP_MAX_DELAY` в `groups.rs`). Отмена прерывает и саму попытку, и паузу, новых попыток после неё нет. Каждая неудача пишет `warn` в span `bridge_group{group=…}` с номером попытки, цепочкой ошибки и следующей паузой. Логика повтора вынесена в `bootstrap_until_ready` с внедряемой фабрикой попытки и покрыта юнит-тестами на виртуальном времени tokio: без Tor, без сети и без реального ожидания (успех с первой попытки, успех после N ошибок, превышение срока попытки, отмена во время попытки, отмена во время паузы, потолок паузы). Тесты написаны, но локально не запускались (их прогонит CI); против реальных мостов не проверялось — живая проверка остаётся открытой (шаг 1 раздела 7).
2. **Watchdog — сделано (задача #563) своим устройством, подключение процессных — нет.** Чего стоят процессные: `spawn_tor_watchdog` по счётчикам попыток и успехов `TorHealth` закрывает каналы живого клиента (`terminate_all_channels`), но эти счётчики заполняют SOCKS5-путь процесса (`apps/sdk/crates/server/src/server/egress/tor_branch.rs`) и рабочая проба обслуживания мостов (`apps/sdk/crates/runtime/src/bridges/bridge_maintenance.rs:597`; вызов в тесте — `:678`), а onion-хостинг группы их не двигает — у клиента группы такая задача молчала бы всегда. `spawn_bridge_failover_watchdog` читает здоровье мостов из bridge-store процесса и сигналит guard manager arti; для группы это была бы вторая, менее предсказуемая рука на пул из 1–3 мостов, где замена моста по рабочему списку уже решает задачу решительнее. Поэтому обслуживание группы своё: считается вердикт по статусу хостинга. Что осталось: (а) `Running` — последний опубликованный статус, а не свежая проверка. Счётчик обновлений статуса сам по себе этого не лечит: поток статусов, зависший после `Running`, молчит так же, как здоровый сервис без изменений. Периодическая проба — отдельный механизм со своей ценой (лишний трафик через клиента группы) и своим риском (ложные пересоздания), поэтому здесь он не реализован и остаётся ограничением; (б) типизированная причина различает исчерпанное ожидание адреса (`ServiceFailure::AddressUnavailable`) и неизлечимые отказы, но `AddressUnavailable` может быть и следствием постоянной проблемы с ключом, поэтому бюджет `MAX_FAILED_RESTARTS` иногда тратится впустую.
3. **Пул — снимок на старте — снято (задача #563).** Стартовый набор по-прежнему берётся из `settings.bridges`, но дальше группа заявляет мосты из рабочего списка процесса перед каждой попыткой бутстрапа и на каждом тике: выбор и резервирование — под одним захватом, поэтому две группы не получат один свободный мост; замена частичная, число мостов не меняется, остаток мёртвых держится до появления свободного; при успешной переконфигурации клиента старые мосты отпускаются в пул, при отказе клиента зарезервированные (новые) мосты возвращаются в пул, а прежний набор остаётся за группой; при окончательной остановке группы её мосты освобождаются. Остановка поколения дожидается фактического завершения задач замены и хостинга и только потом отдаёт клиент из слота и читает мосты для следующего поколения. Что осталось: (в) «мёртв» выводится из состава рабочего списка, а не из здоровья конкретного моста (процесс может держать набор, пока маршрут работает) — нужна явная правка runtime: отдать из runtime запрос «этот мост жив?» поверх bridge-store (сейчас bridge-store в `tor-socks5-server` только dev-зависимость, поэтому сервер такой запрос сделать не может); (г) глобальный слой наблюдений guard manager в CLI (`apps/socks5-proxy/src/process/logging.rs`) принимает события всех клиентов процесса в одну очередь, и отказы guard'ов клиента группы могут попасть в запись процессного bridge-store при совпадении отпечатка; (д) ожидание завершения задачи после abort не ограничено сверху: задача, застрявшая в блокирующем вызове, задерживает пересоздание группы. Это выбрано сознательно — реестр не должен меняться задачей завершённого поколения, — но цена — задержка восстановления.
4. **`bridges: 1` надёжность снижает — снято частично; по умолчанию теперь 2 (задача #564).** С задачей #563 мёртвый мост группы заменяется, но замена приходит только на следующем тике (по умолчанию через 45 с) и только если в рабочем списке процесса есть свободный мост. Сам путь замены только переконфигурирует клиента (`reconfigure_bridges`), хостинг при этом не перезапускается и дескриптор заново не публикуется — публикация повторяется лишь при пересоздании клиента. Пока моста нет, сервисы группы стоят; надёжность выше прежней даёт `bridges` от 2, поэтому по умолчанию стоит 2, а явный `bridges: 1` остаётся осознанным выбором.

Мелочи:

- Раздача стабильна только при неизменных списке мостов и наборе групп. Новая группа с именем раньше по алфавиту сдвигает срезы всех следующих групп, и они стартуют на других мостах.
- Процессный клиент сохраняет весь список, поэтому мосты группы видят и трафик процессного клиента. Разделение по мостам полное только между группами.
- В CI имена новых тестов в логе не видны (nextest не печатает прошедшие). Зелёный итог значит, что они не упали; запуск по имени локально не делался.

По процессу: функция влита и описана в README до живой проверки. Гайд честно помечает её как не проверенную вживую, но рекомендация групп для «много больше 10 сервисов» была преждевременной и заменена на отдельные процессы как проверенный путь.

Закрыто после ревью (задача #562): флаги `--bridge-group`/`--bridges` у `onion new` и `onion import`, запись в группу больше не требует правки файла вручную. Значения проверяются правилами файла, отказ не оставляет ни ключа, ни записи. Пункты 1–5 списка выше не затронуты.

7. **Минимальные правки runtime, нужные для остатка раздела 6.** Три варианта, каждый со своей ценой:
   - *Свежесть статуса.* В onion-крейте публиковать счётчик обновлений `OnionHostStatus` (или отдельный «heartbeat»-статус), а группа в супервизоре перезаводит таймер и при `Running`. Одного счётчика мало: поток статусов, зависший после `Running`, и здоровый сервис без изменений выглядят одинаково, поэтому нужна ещё периодическая проверка (проба через клиента группы или иной признак жизни) — это отдельный механизм со своей ценой (лишний трафик) и риском (ложные пересоздания), и сейчас его нет. Без него «Running» остаётся последним опубликованным значением.
   - *Явный вердикт о мосте.* Отдать из runtime функцию вида `bridge_is_dead(config_path, bridge) -> bool` поверх bridge-store (retired / `max_fails` / `max_circuit_fails`) и звать её из заявки вместо вывода из состава рабочего списка; либо добавить `bridge-store` в зависимости `tor-socks5-server` и читать стор напрямую. Цена: небольшая публичная функция в runtime либо одна строка в манифесте; риск — заявка начнёт сверяться со стором, который обновляет основной клиент, то есть появится вторая точка чтения состояния процесса (только чтение).
   - *Изоляция наблюдений guard manager.* Самый дешёвый честный вариант — не менять `arti-wrapper`, а расширить `ObservationSink`: `exclude(bridges)`/`include_scope`, чтобы `drain_into_store` не считал наблюдения по мостам, закреплённым за группами; сервер зовёт это при заявке и снятии моста. Цена: API и блокировка на пути слива; риск — мост, который одновременно держит и процессный клиент, перестанет учитываться и для процесса. Полностью корректный вариант — свой scope у клиента в `arti-wrapper`/наблюдательном слое (поле у события + фильтр), это заметно больше кода и трогает путь горячих событий.
