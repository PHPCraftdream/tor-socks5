# Группы мостов для onion-сервисов

- **Дата:** 2026-11-20
- **Статус:** реализовано и проверено `cargo check`/`clippy`; тесты логики есть, живого запуска группы против реальных мостов не было.
- **Запрос.** Задавать количество мостов на сервис ради надёжности; в пределе — один конечный сервис на нескольких адресах, у каждого свои мосты.
- **Выбор владельца.** Группы: `bridge_group` + `bridges: N` на записи сервиса.

## 1. Почему нужен отдельный клиент

Arti не знает понятия «мосты этого сервиса»: набор guards, пул onion-цепей и состояние принадлежат одному `TorClient`. Поэтому все сервисы процесса идут через один мост (первый пригодный из первичных guards), а `tor.guard_spread` (1..3) делит цепи между 2–3 мостами сразу для всех сервисов. Свой набор мостов у сервиса возможен только через свой `TorClient` со своим состоянием guards.

В коде уже есть прецедент: одноразовые клиенты проверки моста (`verify_bridge_reachable`) берут свой `state_dir` и общий `cache_dir` процессного клиента, и консенсус не скачивается заново.

## 2. Что сделано

- **Конфиг** (`packages/proxy-config`, файл сервисов): `bridge_group` (`a-z 0-9 _ -`, до 25 байт; имя становится каталогом, поэтому только нижний регистр) и `bridges` (1..=8, по умолчанию 1; только вместе с `bridge_group`). Включённые сервисы одной группы обязаны указывать одинаковое `bridges`. Без `bridge_group` сервис работает как раньше.
- **Раздача мостов** (`apps/sdk/crates/server/src/onion/groups.rs`): рабочий список процесса сортируется по строке моста, группы идут в порядке имени, каждая получает свой непрерывный срез; при нехватке срезы заворачиваются и пересекаются (предупреждение), при `bridges` больше списка группа получает весь список (предупреждение). Тот же список даёт ту же раздачу при каждом запуске.
- **Клиент группы:** `Settings` процессного клиента, но `bridges` группы, `state_dir = <arti base>/group-<имя>`, `cache_dir` общий с процессным клиентом, `guard_spread = min(bridges, 3)`. Без мостов клиент не создаётся (клиент без мостов вышел бы в Tor напрямую).
- **Хостинг:** на группу свой `TorHandle` и свой `OnionHost` со своим keystore (`group-<имя>/state/keystore`) и своей блокировкой; сервисы без группы идут через процессный клиент, как раньше. Если все сервисы в группах, супервизор сам держит блокировку keystore процессного клиента, чтобы `onion new`/`remove` по-прежнему отказывали при работающем сервере.
- **Логи:** строки группы идут в span `bridge_group{group=<имя>}`, строки сервиса несут `nickname`.

## 3. Критерии приёмки

1. Конфиг без новых полей читается и пишется как раньше; новые поля не появляются в файле, пока не заданы.
2. Неверные значения отвергаются с путём `services[i].…`: `bridges` без группы, `bridges` вне 1..=8, имя группы с верхним регистром/пробелом/точкой/длиннее 25, разное `bridges` у включённых сервисов группы.
3. Раздача: группы получают непересекающиеся мосты, пока хватает списка; раздача не зависит от порядка входного списка; нехватка списка не падает, а предупреждает.
4. Клиент группы: свои `state_dir`/keystore, общий кэш, только мосты группы, отказ без мостов.
5. `cargo check`, `clippy -D warnings`, `fmt`, структурные линты чистые; тесты зелёные в CI.

## 4. Не-цели

- Подмена мёртвых мостов группы на ходу (у процессного клиента есть обслуживание мостов, у группы нет).
- Запрос новых мостов, проверка живости и ротация по группам.
- Разный `circuit_hops` у групп (остаётся одно значение на процесс).
- Android (там onion-хостинг по умолчанию выключен).
- Флаги `--bridge-group`/`--bridges` у `onion new`; поля пишутся в файл вручную.

## 5. Риски и что не проверено

- **Не измерено вживую:** запуск клиента группы против реальных мостов, время до первого статуса, поведение при отказе одного моста группы. Нужен прогон с разрешения владельца (нагрузка на мосты).
- **Общий кэш каталога.** Клиент группы читает кэш процессного клиента (второй писатель блокируется, группа работает в режиме чтения). Это предположение опирается на прецедент проверочных клиентов; для долгоживущего клиента не проверено. Если консенсус в кэше устареет, пока процессный клиент не обновил его, клиент группы ждёт обновления.
- **Мосты группы не заменяются.** Если все мосты группы отказали, её сервисы стоят до перезапуска. Для надёжности брать `bridges` не меньше 2 и держать в списке запас.
- **Цена:** на группу один PT-процесс, свой набор соединений и бутстрап. 30 групп по одному сервису — тяжело; предпочтительны группы из нескольких сервисов.
- **Анонимность:** мосты группы видят только трафик группы (лучше для разделения), но суммарно больше мостов видят IP сервера.

## 6. Следующие шаги

1. Живая проверка одной группы с `bridges: 2` (с разрешения): время старта, статус, отказ одного моста.
2. Если подтвердится, обслуживание мостов на группу (замена мёртвых).
3. Флаги `onion new` для групп.
