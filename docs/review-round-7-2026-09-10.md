# Ревью tor-socks5 — раунд 7

Дата: 2026-09-10. Проверенный HEAD: `8bab8bc46c6554f2c0b2fe8989b92ccc24259df5`.

Проверены изменения после шестого раунда и связанные пути в bridge-probe,
bridge-fetcher, bridge-store, CandidatePool, StoreWriter и Android engine.
Основной фокус — идентичность соединений, порядок публикации состояния,
жизненный цикл кешей, ошибки I/O и лишнее удержание памяти.

Шкала: **P0** — критическая проблема без дополнительных условий; **P1** —
срочное исправление с большим воздействием; **P2** — дефект, требующий
исправления при указанных условиях; **P3** — менее существенный дефект или
оптимизация. P0/P1 в проверенном объёме не обнаружены.

Все восемь пунктов ниже открыты. Это отчёт ревью; production-код и тесты
в этом раунде не изменялись. Для каждого дефекта прослежены конкретные
состояния кода; новые сценарии отказа не запускались как regression tests.

Исправления шестого раунда учитывались при отборе: публикация DNS теперь
атомарна относительно читателя, обычные labels переживают round-trip,
разные URL/path проходят fetcher и pool, а одинаковые hostname разделяют
lookup. TS7-01/02 и TS7-03 описывают оставшиеся условия TS6-01 и TS6-03
после этих изменений. Глубокая копия store на мутацию из TS6-04 повторно
не выставляется как новая находка.

## TS7-01 — P2: номер поколения не отражает порядок snapshot

**Место:** [снятие snapshot](../packages/bridge-probe/src/dns.rs#L498-L532),
[выдача поколения](../packages/bridge-probe/src/dns.rs#L540-L545),
[проверка перед публикацией](../packages/bridge-probe/src/dns.rs#L588-L601).

Оба snapshot уже созданы и их locks отпущены, когда save получает `gen`.
На многопоточном executor допускается следующий порядок:

1. A снимает старое состояние и приостанавливается до выдачи поколения.
2. Кеш обновляется; B снимает новое состояние, получает поколение 1 и публикует его.
3. A получает поколение 2 и заменяет файл своим старым состоянием.

Проверка `gen == latest` пропускает A. Ни atomic rename, ни publication
mutex не определяют возраст данных, захваченных до этого номера.
Предыдущая проблема перемешивания байтов устранена, но обещание не
заменять уже опубликованный новый snapshot старым остаётся нарушенным.
Условие — перекрывающиеся вызовы одного path на разных потоках; обычный
последовательный watchdog сам по себе такого порядка не создаёт.

**Исправление:** сериализовать получение snapshot и его номера в одной
очереди владельца path либо использовать ревизию состояния, захваченную
вместе с данными. Порядок постановки blocking jobs не заменяет эту связь.

**Критерий проверки:** остановить A после snapshot, полностью опубликовать B
с более свежими данными, затем продолжить A. После обоих завершений на диске
должно остаться состояние B.

## TS7-02 — P2: начатый save ошибочно считается состоявшейся публикацией

**Место:** [увеличение generation до I/O](../packages/bridge-probe/src/dns.rs#L540-L549),
[ошибка writer](../packages/bridge-probe/src/dns.rs#L578-L581),
[успешный пропуск старого job](../packages/bridge-probe/src/dns.rs#L588-L601).

`latest` означает последний начатый save, а не последнюю успешную запись.
Пусть A с поколением 1 ещё пишет свой temp; B получает поколение 2, но его
write завершается ошибкой. A успешно дописывает temp, видит `latest == 2`,
удаляет свой файл и возвращает `Ok(())`. Ни A, ни B не опубликованы: конечный
файл остаётся прежним или отсутствует. Аналогичен случай ошибки rename у B.

Комментарий у пропуска утверждает, что новый snapshot уже победил, хотя
результат B не проверяется и A его не ожидает. Даже если B пока не упал,
успешное завершение A не означает, что какой-либо новый snapshot доступен
на диске. Это отдельный дефект подтверждения save при корректном порядке
номеров, а не перестановка snapshot из TS7-01.

**Исправление:** различать принятые и опубликованные поколения. При
объединении нескольких save их подтверждения должны зависеть от фактической
публикации покрывающего snapshot. Ошибка нового job должна либо разрешать
публикацию подходящего старого, либо доходить до ожидающих результат callers.

**Критерий проверки:** управляемо задержать A, завершить B ошибкой write
и отдельно rename, затем продолжить A. `Ok` допустим только при наличии
соответствующего успешно опубликованного состояния.

## TS7-03 — P2: канонический endpoint описывает не всё соединение

**Место:** [сокращение PreparedTarget до tuple](../packages/bridge-probe/src/probe/mod.rs#L261-L273),
[поля target](../packages/bridge-probe/src/probe/mod.rs#L137-L153),
[dedup](../packages/bridge-fetcher/src/dedup.rs#L16-L30),
[ключ pool](../apps/socks5-proxy/src/candidate_pool.rs#L40-L54).

Новый ключ содержит dial host, port и path/query. При этом probe реально
использует ещё `sni`, `host_header` и `use_tls`. Эти поля выбрасываются.
При одинаковых ORPort и fingerprint совпадают, например:

- `url=https://edge.example/x servername=old.example` и тот же URL с
  `servername=new.example`: разные TLS-имена и HTTP Host;
- `url=http://edge.example:443/x` и `url=https://edge.example/x`:
  один dial address, но plain HTTP и TLS;
- разные URL hosts с одинаковыми path и `addr=` override: разные virtual hosts
  одного фактического сервера.

First-wins оставляет первый вариант и может удалить рабочую конфигурацию
до probe. TS6-03 исправлен для разных path, но не для остальных используемых
параметров соединения. Полный набор полей уже вычислен в PreparedTarget;
повторно разбирать параметры для определения их значимости не требуется.

**Исправление:** представить идентичность carrier отдельным типом и включить
в неё все значимые поля подготовленного соединения, включая TLS и HTTP
authority. Использовать один тип в fetcher и pool.

**Критерий проверки:** перечисленные пары сохраняются как разные кандидаты;
действительно эквивалентные настройки по-прежнему дедуплицируются.

## TS7-04 — P2: новый URL наследует доказательства и отказы старого

**Место:** [ключ BridgeStore](../packages/bridge-store/src/lib.rs#L190-L197),
[обновление bridge без сброса всей истории](../packages/bridge-store/src/observe.rs#L16-L39),
[сопоставление alive/probed](../packages/bridge-store/src/observe.rs#L62-L72),
[отбор channel-proven](../packages/bridge-store/src/stats.rs#L24-L28).

Fetcher и CandidatePool теперь допускают `/old` и `/new` одного relay,
но BridgeStore по-прежнему использует только transport, ORPort и fingerprint.
Две прошедшие ранний dedup конфигурации попадают в одну health-запись.

После channel/circuit success на `/old` успешный TCP probe `/new` заменяет
`e.bridge`, сохраняя прежние `channel_ok_count` и `verified_count`. Экспорт
channel-proven выдаёт `/new`, хотя эти доказательства относятся к другому
carrier. В обратном случае permanent failure старого варианта остаётся
в `circuit_fails`: новый вариант считается retired ещё до собственной проверки.
Этот фильтр применяется при [настройке Tor](../apps/socks5-proxy/src/tor_setup.rs#L65-L72).

Кроме того, success одного endpoint помещает общий ключ в `alive_keys`,
поэтому failure другого в том же probe round пропускается. Это отдельная
ошибка хранения и интерпретации здоровья после раннего отбора из TS7-03.

**Исправление:** разделить relay-level сведения и доказательства доступности
конкретного carrier. Endpoint-зависимые failures, retirement и successes
должны адресоваться соответствующей конфигурацией. Согласовать lookup,
наблюдения, persistence и экспорт.

**Критерий проверки:** успех `/old` не делает `/new` channel-proven; отказ
или retirement `/old` не запрещает `/new`; два разных исхода одного probe
round сохраняются отдельно и переживают save/load.

## TS7-05 — P2: Weak не удаляет ключ и собственную allocation

**Место:** [INFLIGHT_DOH](../packages/bridge-probe/src/probe/dns_resolution.rs#L241-L255),
[вставка и завершение lookup](../packages/bridge-probe/src/probe/dns_resolution.rs#L272-L296).

Глобальная HashMap никогда не удаляет hostname: после завершения всех
waiters в ней остаются String и Weak. Следующий lookup другого имени
добавляет ещё одну запись. Неудачные lookup также оставляют записи.
Повторный lookup того же имени только заменяет его прежний Weak.

Сам результат OnceCell уничтожается при исчезновении strong references,
но Weak удерживает allocation Arc до собственного Drop. Это прямо следует
из [контракта Weak](https://doc.rust-lang.org/std/sync/struct.Weak.html).
Следовательно, память реестра составляет O(U), где U — число различных
hostname за жизнь процесса, даже при последовательной обработке.

Утверждение комментария об ограничении количеством активных probes неверно:
лимит конкурентности не ограничивает исторические записи. `DNS_CACHE_CAP`
ограничивает другую таблицу и здесь не помогает. Обновляемые источники
мостов создают реальный churn ключей длительно работающего VPN.

**Исправление:** удалять завершённые записи с проверкой идентичности cell
либо регулярно убирать мёртвые Weak и ограничивать реестр. Очистка старого
lookup не должна удалить уже начавшийся новый lookup того же имени.

**Критерий проверки:** после завершения последовательных lookup разных
hostname размер реестра возвращается к заданной границе; живые waiters
продолжают разделять один результат, отмена и retry остаются корректными.

## TS7-06 — P2: flush не отделяет незавершённые lookup прежней сети

**Место:** [flush_dns_cache](../packages/bridge-probe/src/dns.rs#L291-L306),
[присоединение к cell и кеширование ответа](../packages/bridge-probe/src/probe/dns_resolution.rs#L272-L295),
[reset Android watchdog](../packages/android-ffi/src/engine_bootstrap.rs#L726-L745).

Flush очищает ответы и scores, но не меняет поколение lookup и не отделяет
INFLIGHT_DOH. Если запрос host уже начался, вызов после flush находит его
живую cell и присоединяется к нему. Ответ старого запроса публикуется через
`remember_doh_answer` как свежий и используется новым caller.

Таким образом, после смены сети восстановление каналов может снова получить
адрес прежней сети без отдельного нового поиска. Это противоречит назначению
flush и сильнее простого сохранения старого disk fallback: такой ответ
получает обычный положительный TTL и обходит цепочку fallback. Новый
single-flight добавляет именно присоединение post-flush caller к старой работе.

**Исправление:** включить сетевое поколение в ключ совместного lookup и
проверять его при публикации ответа. Согласовать смену поколения и очистку
кеша; одной очистки HashMap недостаточно, пока старые jobs ещё завершаются.

**Критерий проверки:** задержать lookup A, сделать flush, начать B того же
host, затем завершить A. B должен искать в новом поколении, а A не должен
наполнять его кеш. Порядок проверяется сигналами, без временных предположений.

## TS7-07 — P3: новый decoder неоднозначно читает старые labels

**Место:** [безусловное percent decoding](../packages/bridge-store/src/persistence.rs#L91-L112),
[чтение src](../packages/bridge-store/src/persistence.rs#L160-L169),
[legacy-тест](../packages/bridge-store/src/tests/persistence.rs#L196-L225).

До изменения `src=` хранил labels буквально. Теперь любой `%HH` декодируется,
а признак encoding в файле отсутствует. Старый label `feed%2Cbackup`
превращается в `feed,backup`, `feed%20one` — в `feed one`, `%FF` — в символ
замены. Следующий save закрепляет уже изменённое значение; прежний label
восстановить из него нельзя.

Тест с `100%` проверяет только percent без двух hex-цифр и не покрывает
неоднозначность. Современный encode/decode round-trip корректен; проблема
возникает при загрузке допустимых старых файлов и затрагивает attribution.

**Исправление:** обозначать encoding отдельным metadata-полем либо новым
именем поля источников. Старый немаркированный формат читать буквально.

**Критерий проверки:** legacy labels с `%20`, `%2C`, `%25` и `%FF` сохраняются
буквально; маркированный новый формат правильно восстанавливает пробелы,
запятые, percent и Unicode.

## TS7-08 — P3: temp-файл не удаляется при неудачном rename

**Место:** [уникальный temp и cleanup ошибок write](../packages/bridge-probe/src/dns.rs#L572-L580),
[возврат ошибки rename](../packages/bridge-probe/src/dns.rs#L599-L601),
[периодический save](../packages/android-ffi/src/engine_bootstrap.rs#L428-L434).

После успешного write ошибка rename возвращается напрямую, оставляя temp.
Например, destination занят несовместимым файловым handle на Windows или
является каталогом, тогда как создание соседнего temp разрешено. Следующий
save получает новый `gen` и создаёт ещё один файл вместо повторного
использования или удаления предыдущего.

При длительном отказе публикации занимаемое место растёт на полный snapshot
за попытку. Очистка реализована для ошибки write и для superseded job,
поэтому именно третья ветка завершения остаётся без владельца temp.

**Исправление:** cleanup guard для созданного временного файла; disarm только
после успешной передачи имени через rename. Сохранять исходную ошибку rename.

**Критерий проверки:** после нескольких ошибок публикации нет оставленных
temp-файлов, прежний destination сохранён, последующая успешная попытка работает.

## Проверки и границы выводов

На Windows прошёл `cargo test --locked -p bridge-probe -p bridge-fetcher
-p bridge-store --lib -j 2`: **98 + 85 + 58 = 241 passed**, без failed/ignored.
Также прошли `cargo fmt --all -- --check` и `git diff --check`.
Статический подсчёт tracked first-party Rust-файлов не обнаружил превышений
лимита 1000 строк. Проверены относительные ссылки отчёта и отсутствие частных путей.

Тесты выполнялись с зависимостями Cargo.lock, включая Tokio 1.52.3 и
tokio-util 0.7.18. Cargo сообщил существующее предупреждение future

Полный workspace, clippy, Android/MSRV builds и benchmarks в этом раунде
не запускались. Измеренного ускорения или частоты production-сбоев отчёт не заявляет.

Сначала следует согласовать snapshot/publication и идентичность carrier
(TS7-01–04), затем жизненный цикл DoH (TS7-05/06), после них совместимость
labels и cleanup временных файлов (TS7-07/08).
