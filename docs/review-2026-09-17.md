## Ревью текущих правок

### TS17-01 — P2: не удалять temp-файлы живого чужого writer

Места: [bridge-store persistence](../packages/bridge-store/src/persistence.rs#L26), [Config cleanup](../packages/proxy-config/src/lib.rs#L26), [CandidatePool cleanup](../apps/socks5-proxy/src/candidate_pool.rs#L46). Вызовы cleanup находятся внутри обычных `load` / `from_file`.

**Механизм.** Единственная проверка владельца — `parsed_pid != Some(std::process::id())`. Другой PID означает другой процесс, но не означает завершившийся процесс. Чтение не обязано брать transaction lock: например, CLI загружает config до начала своей транзакции, а read-only потребители читают bridge-store напрямую.

**Сценарий.** Процесс A записал `.state.log.<A>.42.tmp` и ещё не переименовал его. Процесс B читает `state.log`, cleanup удаляет temp A. Последующий rename A завершается ошибкой. На Unix возможен unlink даже открытого файла; на Windows есть как минимум окно между закрытием file handle и rename. Защита только собственного PID закрывает предыдущий тестовый сбой внутри процесса, но оставляет межпроцессную гонку.

**Влияние.** Потеря текущего сохранения, отказ config promotion, повторные ошибки publisher. Дополнительно malformed suffix тоже проходит проверку: `None != Some(current_pid)`; маска не является доказательством владения файлом.

**Доказательство.** В отдельный временный Rust harness без изменения репозитория скопированы тела трёх cleanup-функций непосредственно из текущих исходников. В имени temp использован PID живого родительского Python-процесса. Все три функции удалили файл. Это проверка самих helper-функций, не полноценный end-to-end тест двух daemon.

**Исправление.** Удалять только доказанно неиспользуемые файлы: согласованный межпроцессный механизм владения/блокировки, совместимый со всеми writer. Не выводить смерть процесса из несовпадения PID. Проверять точный формат имени. Добавить regression со вторым живым процессом, припаркованным перед rename, и читателем без write-lock.

### TS17-02 — P2: timeout не гарантирует завершение blocking verifier

Места: [внешний timeout](../apps/socks5-proxy/src/fetch_merge.rs#L404), [spawn_blocking](../apps/socks5-proxy/src/bridge_verifier.rs#L93), [snapshot до проверки бюджета](../apps/socks5-proxy/src/bridge_verifier.rs#L519), [SQLite backup и копирование](../packages/bridge-verify-core/src/snapshot.rs#L23).

**Механизм.** `timeout_at` отменяет `verify_for_admission`, когда тот ожидает `JoinHandle`. Уже запущенный `spawn_blocking` продолжает работу. Перед per-bridge deadline-check выполняется `snapshot_cache_dir`: у SQLite свой 15-секундный бюджет, рекурсивное копирование файлов общего deadline не принимает. Запас `ADMISSION_JOIN_MARGIN = 50ms` этого не ограничивает. Очередь blocking pool также может задержать начало worker.

**Сценарий.** Verifier получает `VERIFY_LOCK` незадолго до общего deadline и начинает snapshot. Внешний timeout возвращает кандидата в deferred и отпускает pool-lock, пока worker продолжает копирование под `VERIFY_LOCK`. Следующие проверки конкурируют с работой, которую caller уже считает завершённой.

**Влияние.** Возвращается detached работа и нарушается заявленная гарантия владения worker; это не прежнее длительное удержание pool-lock — оно действительно сокращено. Тест с `pending::<bool>()` подтверждает лишь отмену async checker, но ничего не доказывает о завершении реального blocking worker.

**Исправление.** Разделить срок принятия admission-решения и обязательное завершение worker. Передавать deadline/cancellation в snapshot и сохранить владельца `JoinHandle` до cleanup; либо изменить транзакционную схему, чтобы cleanup можно было дождаться вне pool-lock. Проверять событие завершения worker, а не только возврат кандидата.

### TS17-03 — P3: snapshot может попасть между очисткой live-cache и переносом fallback

Места: [flush](../packages/bridge-probe/src/dns.rs#L404), [capture](../packages/bridge-probe/src/dns.rs#L707).

**Механизм.** Flush копирует ответы, очищает live-cache и отпускает его mutex; только затем отдельными вызовами заполняет disk fallback. Snapshot использует свой per-path gate, с которым flush не синхронизирован, и может прочитать оба store в промежутке.

**Сценарий.** A очищает live и приостанавливается перед fallback merge. B захватывает пустые live и disk, получает новое save-поколение. A заканчивает merge. B публикует пустой файл; даже старый непустой save может быть отклонён по поколению. До следующего save файл лишён сохранённых ответов.

**Граница вывода.** Это подтверждённое чередование публичных `flush`/`save` API. Внутри одного watchdog они вызываются последовательно; частоту такого чередования в приложении не измеряли. Поэтому P3, а не утверждение о постоянной потере DNS на каждом network reset.

**Исправление.** Сделать переход live → fallback неделимым для snapshot либо синхронизировать его общим gate с задокументированным порядком lock. Regression должен парковать flush после `clear`, до merge, и запускать save в этот промежуток.

### TS17-04 — P3: DNS cleanup никогда не совпадает с обычным temp writer

Места: [prefix](../packages/bridge-probe/src/dns.rs#L582), [writer name](../packages/bridge-probe/src/dns.rs#L640).

Cleanup ищет `.<file>.<pid>.<gen>.tmp`, writer создаёт `<file>.<pid>.<gen>.tmp` без начальной точки. Поэтому crash leftovers DNS остаются на диске. Временный harness с телом настоящего cleanup подтвердил: `dns-cache.txt.4294967295.42.tmp` переживает загрузку. Исправить общий генератор/распознаватель имени вместе с безопасным владением из TS17-01; тестировать имя, реально создаваемое writer.

### TS17-05 — P3: directory fsync пропускается для конфигурации по умолчанию

Места: [config parent](../packages/proxy-config/src/lib.rs#L52), [store parent](../packages/bridge-store/src/persistence.rs#L52), [pool parent](../apps/socks5-proxy/src/candidate_pool.rs#L72), `sync_persist_parent_dir` в [dns.rs](../packages/bridge-probe/src/dns.rs).

Для `Path::new("tor-socks5.ktav")` вызов `parent()` возвращает `Some("")`, а не `None`. `unwrap_or_else(|| Path::new("."))` оставляет пустой путь. На Unix `File::open("")` не открывает текущий каталог; ошибка игнорируется. Та же ошибка мешает `read_dir`-cleanup относительных путей.

Это затрагивает штатный запуск с именем config без каталога: добавленная гарантия сохранности rename после сбоя питания не действует. Значение `parent()` проверено локально; Unix crash/power-loss тест не выполнялся. Исправление: отфильтровать пустого родителя до fallback на `.`; проверить helper на bare filename и на вложенном пути.

### TS17-06 — P3: R-08 добавляет аллокации на том hot path, который должен ускорять

Места: [LAST_LOOKUP_KEY](../packages/bridge-store/src/lib.rs#L55), [key_of](../packages/bridge-store/src/lib.rs#L206), [Android comparator](../packages/android-ffi/src/engine_bridges.rs#L206).

Comparator запрашивает `channel_ok_count(B)`, `channel_ok_count(A)`, при равенстве — `ok_count(B)`, `ok_count(A)`. Для различных A/B одноэлементный кэш промахивается на всех этих чередованиях. Каждый miss по-прежнему строит identity и разбирает WebTunnel URL, дополнительно клонирует весь `BridgeLine` с params и создаёт `Arc`. Полный проход по различным bridges также состоит преимущественно из misses.

Повторные подряд чтения одного bridge выигрывают; утверждение об ускорении comparator неверно. `Entry::key` не хранит отдельный кэш entry, несмотря на комментарий. Семантический round-trip тест агента не измеряет число построений ключа.

Исправление: заранее снять ranking counters один раз на bridge (`sort_by_cached_key` или decorate/sort), использовать уже имеющиеся map keys при обходе. Проверять число вычислений/аллокаций детерминированным счётчиком; производительный benchmark в этом ревью не запускался.

## Общий код вне diff

### TS17-07 — P2: TOFU и CLI не сериализуют реестр пользователей между процессами

Места: [resolve_init](../packages/auth/src/state.rs#L301), [повторное чтение](../packages/auth/src/state.rs#L307), [save](../packages/auth/src/state.rs#L358), [CLI mutations](../apps/socks5-proxy/src/users_cli.rs#L232), [обещание в документации](auth.md#trust-on-first-use--init).

`self.users.write()` защищает только один `AuthState`. CLI выполняет отдельный load → mutate → save без общего file lock. Повторное чтение перед записью не делает весь read-modify-write атомарным.

Контрпример: daemon читает `{alice=init, bob=enabled}`; CLI отключает bob и сохраняет; daemon сохраняет свой snapshot с паролем alice и старым `bob=enabled`. В обратном порядке CLI может вернуть уже подтверждённый пароль alice в `init`. Две CLI-мутации также могут потерять друг друга. Атомарный rename защищает байты файла, но не эти изменения.

Влияние: потеря отключения пользователя / смены пароля; повторная доступность TOFU-аккаунта после перезапуска. Это иной остаточный механизм, чем ранее исправленная гонка двух TOFU внутри одного процесса. Исправление: общий межпроцессный lock вокруг полного RMW во всех writer; subprocess-регрессия TOFU против disable/set-password.

### TS17-08 — P2: сбой config promotion теряет уже проверенные кандидаты

Места: [save pool](../apps/socks5-proxy/src/fetch_merge.rs#L429), [поздняя promotion](../apps/socks5-proxy/src/fetch_merge.rs#L479), [config lock](../apps/socks5-proxy/src/fetch_merge.rs#L500).

Успешные кандидаты уже удалены из pool и это сохранено до попытки обновить config. Если config-lock занят до таймаута, config временно нечитаем или запись завершается ошибкой, `promote_bridges_in_config` возвращает Err без восстановления кандидатов. Их нет ни в pool, ни в рабочем config; новый fetch может вернуть их, но гарантии такого fetch нет. Health-store запись не заменяет рабочую конфигурацию.

Порядок существовал до diff; добавленный bounded config-lock вводит ещё один нормальный путь такого отказа. Исправление: подтверждать удаление после успешной идемпотентной promotion либо иметь durable pending/journal и восстановление. Не возвращать кандидата через запись старого snapshot поверх конкурентного refresh. Regression: успешная проверка + принудительная ошибка config-write, затем повторный drain без нового fetch.

## Что в правках подтверждено

- R-02 учитывает только `Ok(true)` как доказательство конкретного канала.
- R-03 сериализует три обнаруженных config RMW между участвующими writer; TS17-01 относится к новым побочным действиям читателей.
- Settings-based конструкторы R-04 передают iat override в target builder, включая bootstrap с уведомлениями. Raw-config API отдельно не доказывает настройку override.
- R-05 сохраняет generation/version fencing и разрешает invalidation после отказа ограниченного набора адресов; protocol failures не дают списка TCP-failed адресов.
- R-06 проверяет свежий positive под cache-lock; `insert_capped` назначает реальные generation/version.
- R-07 ограничивает sweep длиной очереди на начало прохода.
- R-10 переносит engine/watchdog store I/O в blocking jobs. JNI manual-probe сохраняет данные уже после `block_on`, то есть это не оставшийся async-worker путь.
- R-11 очищает warm failures при stall reset; R-12 различает внешний сокращённый timeout и ошибку, возвращённую самим stream future.
- R-14 использует общий `BridgeIdentity` в pool и fetcher.

Общий проход дополнительно охватил auth/TOFU/users CLI, SOCKS5 setup, bridge-fetcher direct path, shared cache snapshot, Cargo/CI и границу с ptrs-gesher. Это ограниченное ручное ревью, не полный аудит всего vendored Arti, Android/Kotlin-приложения, криптографии или зависимостей по CVE. Агенты не запускались.

Фактические проверки этого прохода: чтение кода/diff/истории, lockfile inspection, отдельный Rust harness из настоящих cleanup-функций (TS17-01/04), проверка `Path::parent` (TS17-05). Сеть мостов, искусственная нагрузка, power-loss и Android device tests не запускались. Полный workspace test/clippy повторно не запускались: их успешный результат относится к предыдущему проходу; он не доказывает отсутствие перечисленных дефектов. Сценарии TS17-02/03/06/07/08 подтверждены трассировкой кода, не новым интеграционным тестом.

Разрешённые версии из `Cargo.lock`: Tokio 1.52.3, Serde 1.0.228, rustls 0.23.40, Hickory 0.26.1. `ptrs-gesher-lyrebird` и `ptrs-gesher-webtunnel` берутся из registry 0.5.3: соседний checkout ptrs-gesher автоматически не входит в эту сборку.
