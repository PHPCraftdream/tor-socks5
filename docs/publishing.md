# tor-socks5 — runbook публикации на crates.io

- **Дата:** 2026-09-21
- **Статус:** runbook — процедура публикации записана ДО первой публикации и
  защищена от регрессий CI. Публиковать СЕЙЧАС ничего нельзя: вендорный гейт
  закрыт (§4), публикуемое множество пусто (§1). Документ оживает только после
  слияния единого крейта и открытия гейта.
- **Дизайн:** [docs/sdk-package-design.md](sdk-package-design.md) (SDK-01) —
  что публикуем (цельный пакет `tor-socks5`, §1), карта модулей и стратегия
  перехода (§2, §6), вендорный гейт (§4), semver/MSRV (§7).
- **Исследование:**
  [docs/crates-io-publish-research-2026-09-19.md](crates-io-publish-research-2026-09-19.md),
  далее «research»: §1 — `[patch.crates-io]` не переносится published-крейтом;
  §6 — android-ffi вне crates.io.
- **Enforcement (автоматика, не память):**
  [scripts/publishable-crates.sh](../scripts/publishable-crates.sh) — единственный
  список публикуемого; [scripts/check-publish-guard.sh](../scripts/check-publish-guard.sh)
  (CI-джоб `publish-guard`) — «всё, кроме списка, обязано быть `publish = false`»;
  [scripts/check-packageability.sh](../scripts/check-packageability.sh)
  (CI-джоб `packageability`) — упаковываемость публикуемого.

---

## 1. Что публикуется и что нет

Публикуется **ровно один артефакт**: цельный крейт **`tor-socks5`** (решение
SDK-01, §1 — форма «физическое слияние библиотечных крейтов + фичи»).

**Состояние на 2026-09-21:** этого крейта ещё не существует — слияние
(docs/sdk-package-design.md §6) не начато. В репозитории 20 пакетных
манифестов (13 first-party членов воркспейса + 7 vendor-форков), и у **всех**
стоит `publish = false`. Проверка одной командой:

```sh
sh scripts/publishable-crates.sh   # пустой вывод = публиковать нечего
```

Список пуст ⇒ CI-джоб `packageability` проходит явным no-op
(«no publishable crates, skipping»), а `publish-guard` требует
`publish = false` у каждого манифеста. Публикуемое множество станет непустым
только одним способом: имя крейта добавляют в
`scripts/publishable-crates.sh` и в том же изменении снимают
`publish = false` с его манифеста (гард сверяет обе стороны, рассинхрон в
любую сторону валит CI).

**НИКОГДА не публикуются:**

| Что | Почему |
|---|---|
| `vendor/*` — `arti-client`, `saturating-time`, `tor-chanmgr`, `tor-circmgr`, `tor-dirclient`, `tor-dirmgr`, `tor-guardmgr` | форки под **апстримовыми** crates.io-именами: публикация любого = захват чужого крейта (имя занято навсегда — §2). `publish = false` стоит у всех семи |
| `packages/android-ffi` | cdylib-only (`crate-type = ["cdylib"]`, lib name `torsocks5`): Rust-потребителю из него нечего импортировать (research §6); потребитель на Rust ходит по path-зависимости |
| `apps/*` (`socks5-proxy`, `pt-helper`) | CLI-бинари/утилиты-потребители библиотечных крейтов, не библиотеки |
| любой внутренний крейт по отдельности (`persist-lock`, `bridge-probe`, …) | решение SDK-01: один цельный пакет, не семья из 8+ имён; внутренние крейты после слияния становятся модулями и исчезают как единицы публикации |

Автоматизированный enforcement этого правила —
`scripts/check-publish-guard.sh` + CI-джоб `publish-guard`: каждый манифест с
`[package]` обязан иметь `publish = false`, исключение — только для имён из
`scripts/publishable-crates.sh`.

## 2. Необратимость

`cargo publish` необратим в трёх смыслах, каждый — по конструкции crates.io:

1. **Пара имя+версия занята навсегда.** Переиздать `x.y.z` после неудачного
   релиза нельзя — только выпускать `x.y.(z+1)`.
2. **`yank` прячет, но не удаляет.** Заянкнутая версия исчезает из нового
   разрешения зависимостей, но остаётся скачиваемой (точечные требования
   `=x.y.z`, `cargo update --precise`), а уже существующие `Cargo.lock`
   продолжают её использовать.
3. **Выложенный код остаётся доступен навсегда** — `.crate`-тарбол и снимок
   документации не удаляются ни при yank, ни при чём-либо ещё.

Следствие: каждый релиз — решение «навсегда»; ошибка выправляется только
новой версией вперёд. Поэтому предпубликационный чеклист (§3) проходится
целиком при **каждой** публикации, без «мы и так знаем».

## 3. Предпубликационный чеклист

Выполнять по порядку; пункт провален — публикация откладывается.

1. **Зелёный CI** на том же дереве, что публикуется: fmt, clippy, test,
   `publish-guard`, `packageability`, `msrv`, `android` — все джобы.
2. **Множество публикации корректно:** `sh scripts/publishable-crates.sh`
   показывает ровно то, что собираемся выложить — один `tor-socks5`, ничего
   больше. Пустой вывод ⇒ публикация запрещена (гейт §4 не открыт).
3. **`cargo publish --dry-run -p <крейт>` — на реальном публикуемом крейте.**
   Внимание: на сегодняшних плейсхолдерах `--dry-run` падает **по конструкции**
   (проверено 2026-09-21: `error: 'persist-lock' cannot be published. package.publish
   must be set to true…`), это не сбой процедуры. Упаковываемость при
   `publish = false` проверяет `cargo package -p <крейт> --no-verify`
   (проверено: проходит чисто) — ровно это и делает CI-джоб `packageability`.
4. **Осмотреть артефакт глазами:** `cargo package -p <крейт> --list`;
   распаковать `target/package/<крейт>-<версия>.crate` (это tar) и прочитать
   `Cargo.toml` внутри — не исходный манифест, а обработанный Cargo.
5. **`[patch.crates-io]` не влияет на публикуемый артефакт.** Cargo **вырезает**
   секцию при упаковке (research §1): потребитель получит **стоковые**
   arti-крейты с crates.io, никакие vendor-фиксы «не поедут». Проверить
   отсутствие `[patch]` в распакованном манифесте (п. 4). Пока в корневом
   `[patch.crates-io]` есть что-то кроме `tor-circmgr` — публикация с фичей
   `tor` запрещена в принципе (§4).
6. **README и доки:** корневой README — лицо крейта; `[package.metadata.docs.rs]`
   соответствует фича-матрице; `cargo doc --workspace --no-deps` без
   предупреждений (`missing_docs` включён на всех библиотечных крейтах);
   страничные ссылки из README работают на docs.rs.
7. **Версия:** первая — 0.1.0; далее по §5. Запись в `CHANGELOG.md`.
8. **Тег** `v<версия>` на релизном коммите.
9. **Выкладывает человек** (§7): `cargo login` и `cargo publish` — не
   автоматика и не агент.

## 4. Вендорный гейт

**С фичей `tor` пакет честно публиковать нельзя**, пока корневой
`[patch.crates-io]` содержит что-то кроме `tor-circmgr`: published-манифест
не переносит `[patch]`, и потребитель, включивший `tor`, молча соберёт
стоковые `saturating-time`/`tor-dirclient`/`tor-dirmgr`/`tor-chanmgr`/
`tor-guardmgr`/`arti-client` — потеряв все фиксы `vendor/README.md`
(Windows 100%-CPU, вечный bootstrap fetch, отравленный netdir, фатальный
`SQLITE_BUSY`, зомби-каналы, дыры guard-readiness). Это тихая деградация
Tor-клиента — research §1 называет такую публикацию «actively worse than not
publishing at all».

Критерий открытия гейта (все три одновременно), фиксация механики и таблица
апстрим-статусов — **docs/sdk-package-design.md §4**; этот раздел не
переписывает её. До открытия действует вариант (ii) того же документа:
**не публиковать ничего** — ни крейта целиком, ни tor-less «огрызка».

## 5. Политика версий

- **Первая версия — 0.1.0.** До 1.0 действует 0.x-semver: **ломающие изменения
  выпускаются минорным бампом** (0.1 → 0.2) — это штатный режим, а не ЧП
  (sdk-package-design.md §7).
- Фичи и optional-зависимости — только **аддитивно**; изменение default-фич
  (включая расширение default до `full` после открытия гейта) — ломающий
  минор: потребитель без `default-features = false` получает другой граф
  зависимостей.
- **MSRV 1.89** (`rust-version` в `[workspace.package]`, наследуется всеми
  членами). Поднимать только отдельным решением, никогда — попутно с релизом.
- Каждый ломающий минор сопровождается записью в `CHANGELOG.md`.

## 6. Что делать при проблемах

### Имя увели (`tor-socks5` заняли до нашей публикации)

Не оспаривать и не «выбивать» — crates.io таких механизмов не даёт. Выбрать
запасное имя из списка свободных (на 2026-09-20 свободны `tor-socks5-sdk` и
`torsocks5` — sdk-package-design.md §1; **перепроверить** актуальность на
странице имени crates.io), обновить `[package] name` и документацию. Именно
благодаря форме «один крейт» переименование — одна строка манифеста, а не
переименовывание семьи из восьми.

### Опубликована сломанная версия x.y.z

1. `cargo yank --vers x.y.z <крейт>` — спрятать версию из нового разрешения.
   Помнить ограничения §2: это **не удаление**; существующие `Cargo.lock`
   продолжают тянуть версию.
2. Выпустить **патч-релиз** `x.y.(z+1)` (минорный — если проблема ломающая).
3. Записать инцидент и yank в `CHANGELOG.md`.
4. Если yankнули по ошибке — `cargo yank --vers x.y.z --undo <крейт>`.
5. «Перевыпустить» ту же пару имя+версия **нельзя** — не тратить время на
   попытки.

### docs.rs не собрался

1. Открыть лог сборки на `docs.rs/crate/<имя>/<версия>` — причина почти всегда
   в расхождении среды: не те фичи/таргеты из `[package.metadata.docs.rs]`
   либо код под `--cfg docsrs`.
2. Воспроизвести локально параметрами из `[package.metadata.docs.rs]`
   (`all-features` + `rustdoc-args = ["--cfg", "docsrs"]`).
3. Исправляющий релиз — **новая версия** (патч/минор по §5), не перевыпуск.
4. Пока docs.rs красный, в README не ссылаться на нерабочие страницы документации.

### Выложили не то (промах мимо чеклиста)

Немедленный `cargo yank`, оценка ущерба (пара имя+версия сожжена навсегда — §2),
правильный релиз следующей версией, разбор: какой пункт §3 был пропущен и
почему автоматика (`publish-guard`/`packageability`) не остановила.

## 7. Кто выполняет

- Токен crates.io — **личный креденшл владельца репозитория**; `cargo login`
  выполняет человек на своей машине.
- **`cargo publish` и `cargo yank` выполняет человек**, не агент и не CI.
- Агенты и скрипты делают всё **до** шага выкладки: dry-run, `cargo package`,
  осмотр артефакта, бамп версии, тег, CHANGELOG.
- В CI-воркфлоу нет секрета с токеном crates.io — так и оставить; вводить
  автоматическую публикацию (release-подобный workflow с `CARGO_REGISTRY_TOKEN`)
  можно только отдельным решением, взвесив риск компрометации токена.
