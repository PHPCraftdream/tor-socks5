## TS6-01 — P2: async save не упорядочивает записи одного DNS-файла

**Место:** [snapshot и blocking job](../packages/bridge-probe/src/dns.rs#L477-L539),
[реальный writer](../packages/bridge-probe/src/dns.rs#L472-L475).

Каждый вызов снимает собственный snapshot и запускает отдельный
`spawn_blocking`. Между jobs одного path нет очереди, generation check или
блокировки публикации. Writer использует `std::fs::write`, то есть открытие
с truncation и последующую запись непосредственно в конечный файл.

Два конкурентных вызова допускают такой порядок: A открывает и обнуляет
файл, B тоже открывает и обнуляет его, A пишет длинный snapshot, B пишет
короткий с начала. Хвост A остаётся после данных B. Обе операции могут
вернуть успех, хотя файл уже не соответствует ни одному snapshot.
Даже без перемешивания задержанный A способен перезаписать свежий B.

Отмена future после запуска blocking job также не останавливает эту запись.
Следующий вызов может завершиться раньше оставленного job. Условие находки —
перекрывающиеся вызовы одного path; текущий последовательный watchdog сам
по себе не означает, что так происходит на каждом Android tick.

TS5-07 убрал formatting и I/O с async worker, но необходимое владение
публикациями при offload осталось не реализовано. Исправление тестовой
синхронизации TS6-06 сохраняет это production-поведение.

**Исправление:** один владелец записей на path, упорядочивание либо
coalescing snapshot с понятным правилом свежести. Публиковать цель через
отдельный временный файл и atomic replace; atomic replace сам по себе не
предотвращает позднюю публикацию старого snapshot. Завершение jobs должно
учитываться и после отмены вызывающей future.

**Критерий проверки:** управляемо задержать A, завершить B и разрешить A;
проверить правило свежести и целостный итоговый файл. Включить отмену A
после передачи blocking job и два snapshot разной длины.

## TS6-02 — P2: label источника интерпретируется как синтаксис metadata

**Место:** [сериализация sources](../packages/bridge-store/src/persistence.rs#L292-L304),
[tokenization](../packages/bridge-store/src/persistence.rs#L65-L75),
[чтение cfails и src](../packages/bridge-store/src/persistence.rs#L106-L115),
[поступление label](../packages/android-ffi/src/engine_bridges.rs#L255-L285).

`note_source_at` принимает обычную строку. В файле sources объединяются
запятыми без escaping, а reader сначала делит всю строку metadata по
whitespace и затем значение `src=` по запятым. Поэтому label `Tor Project`
после save/load превращается в `Tor`, а `A,B` — в два разных источника.

Последствие затрагивает не только отображение. Label `feed cfails=42`
сериализуется после настоящих health-полей; при загрузке его второй токен
перезаписывает `circuit_fails`. Данные источника получают значение управляющего
синтаксиса. Для этого не нужен повреждённый файл: его создаёт штатный writer.

В конфигурации label описан как
[human-readable String](../packages/proxy-config/src/lib.rs#L438-L446).
Потеря точного label также ломает сопоставление статистики с источником
в [barren_sources](../packages/android-ffi/src/engine_bridges.rs#L232-L252).
Нынешние короткие labels в тестах эти разделители не проверяют.

**Исправление:** ввести однозначное escaping/encoding с версией формата
либо хранить устойчивый ID источника отдельно от отображаемого label.
Сохранить чтение существующих файлов. Замена пробелов и запятых на другой
символ создаст коллизии и не обеспечит round-trip.

**Критерий проверки:** save/load сохраняет точные labels с пробелами,
запятыми, Unicode, переводами строк и текстом `cfails=42`; ни одно health-поле
от label не меняется. Добавить legacy fixture, проверяющий старый формат.

## TS6-03 — P2: dedup теряет альтернативный WebTunnel endpoint

**Место:** [dedup_bridges](../packages/bridge-fetcher/src/dedup.rs#L7-L23),
[ключ CandidatePool](../apps/socks5-proxy/src/candidate_pool.rs#L37-L47),
[отбрасывание уже известного ключа](../apps/socks5-proxy/src/candidate_pool.rs#L101-L108),
[реальный target probe](../packages/bridge-probe/src/probe/mod.rs#L320-L337).

Ключ содержит только transport, `BridgeLine.addr` и fingerprint. Для
WebTunnel `addr` в bridge line может быть косметическим ORPort, а реальный
endpoint задают `url=` и transport overrides. Две строки одного Tor relay
с одинаковым placeholder и fingerprint, но с разными URL/path, получают
одинаковый ключ.

Если первая строка содержит старый неработающий `/old`, а следующая —
исправный `/new`, dedup оставляет только `/old` ещё до проверки достижимости.
Уже сохранённый в CandidatePool вариант также блокирует добавление нового:
`push_unique` не обновляет параметры существующей записи.

Сама функция выполняет обещанный first-wins для своего tuple. Дефект
находится в выборе tuple как идентичности соединения: различимые и реально
используемые transport endpoints объявлены дубликатами. Изменение порядка
источников способно менять единственный оставшийся рабочий вариант.

**Исправление:** разделить идентичность Tor relay и конфигурацию carrier.
Для отбора кандидатов учитывать канонический WebTunnel endpoint, включая
существенные URL/path/query и overrides, либо явно реализовать обновление
конфигурации вместо вечного first-wins. Не включать механически все
несущественные параметры в ключ; согласовать ключи fetcher и pool.

**Критерий проверки:** два WebTunnel URL при одинаковом placeholder и
fingerprint остаются доступными отбору, точные дубликаты удаляются. Свежая
рабочая конфигурация не теряется из-за старой записи в сохранённом pool.

## TS6-04 — P3: защита от panic сделала глубокую копию обязательной

**Место:** [clone, make_mut и замена snapshot](../apps/socks5-proxy/src/bridge_store_writer.rs#L352-L379).

Для исправления TS5-06 actor теперь сохраняет свой Arc и передаёт его
clone в mutation job. Следовательно, `Arc::make_mut` всегда видит shared
владение и копирует весь store, даже когда публикация не выполняется.
M мелких мутаций набора размером S требуют `O(M × S)` копирования и
соответствующих аллокаций. Coalescing файловых записей эту стоимость не
сокращает. Это новый постоянный расход, а не прежняя копия только при
совпадении мутации с публикацией.

Копия выполняется на blocking thread. Но `store = Some(owned)` уничтожает
старый Arc на async worker. Если publisher уже не держит именно этот
snapshot — например, во время retry backoff — там же освобождаются весь
BTreeMap и его строки. Перенос создания копии не переносит её последующий Drop.

**Исправление:** сохранить гарантию переживания panic и вынести тяжёлое
освобождение старого snapshot с async worker. Для снижения числа полных
копий оценить типизированные операции, транзакционный batch или структуру
с разделяемыми узлами вместо непрозрачной произвольной mutation closure.
Это архитектурная стоимость обеспечения rollback, поэтому приоритет P3.

**Критерий проверки:** прежние panic/backoff гарантии остаются; отдельно
контролируются число глубоких копий и поток, выполняющий тяжёлый Drop.
Измеренный выигрыш latency или throughput этот отчёт не утверждает.

## TS6-05 — P3: один холодный hostname разрешается несколькими waves

**Место:** [cache miss и запуск wave](../packages/bridge-probe/src/probe/dns_resolution.rs#L242-L266),
[создание tasks](../packages/bridge-probe/src/probe/dns_resolution.rs#L180-L193),
[параллелизм probes](../packages/bridge-probe/src/probe/batch.rs#L9-L29).

Cache запоминает завершённые ответы, но не выполняющийся lookup. Если H
bridge lines одного fronting host проверяются до первого ответа, каждый
probe видит miss и запускает собственную wave из четырёх attempts.
При H=64 первая волна создаёт 256 attempt tasks вместо четырёх общих.
Повторяются task allocations, String/Arc clones и ожидания admission.

Часть работы нижележащий resolver может обслужить из кеша или через
переиспользуемое соединение; число tasks не равно числу TLS connections.
На уровне bridge-probe совместного владения незавершённым разрешением нет.
Исправление TS5-02 отменяет queued losers при выходе отдельной race,
но не объединяет несколько ещё актуальных races одного host.

**Исправление:** разделяемый in-flight lookup по hostname с результатом
IPs/TTL, после которого каждый caller применяет свой port. Ограничить
число таких записей и определить их очистку; отмена одного waiter не
должна отменять запрос, нужный оставшимся. Учесть смену network generation.

**Критерий проверки:** два одновременных вызова для одного host используют
одну provider wave; разные ports получают корректные SocketAddr. Отмена
одного caller не мешает другому, завершённый failure допускает поздний retry.

## TS6-06 — P2: общий test gate блокировал независимый запуск DNS-тестов

**Статус: исправлен**, коммит `530fa06ea7316867d9cb62ce30c7ffe8de1969fa`.

В исходном HEAD каждый test-build вызов save безусловно попадал в
`persist_write_gate::hold_until_released`. Общий `RELEASE` начинался с false;
открывал его только `save_persisted_dns_cache_does_not_block_the_async_worker`.
Одиночный round-trip test не имел того, кто снимет ожидание. Последовательный
запуск мог остановиться на save раньше, чем дошёл бы до открывающего gate
теста. Полный parallel run скрывал зависимость от порядка исполнения.

Механизм выявлен статически. Вместо общего gate введён
[writer, передаваемый одному вызову](../packages/bridge-probe/src/dns.rs#L472-L539).
[Тест offload](../packages/bridge-probe/src/tests/dns_tests.rs#L599-L655)
использует свои channels: проверяет blocking thread, доступность cache и
executor до release, затем фактическую запись файла. Закрытие sender и
конечный receive timeout исключают бесконечное удержание blocking thread
при panic теста. Polling и сравнение произвольных задержек удалены.

**Проверено после исправления:** одиночный round-trip — 1 passed; весь
`bridge-probe --lib` — 88 passed; DNS-тесты с `--test-threads=1` — 31 passed.
Ни одного failed или ignored в этих запусках. Исправление не отложено
в список будущих работ.
