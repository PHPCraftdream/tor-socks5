# Release license bundle: процесс и границы доверия

Это описание текущего wiring и будущего пути допуска, а не заявление об успешном CI, опубликованном релизе или юридическом соответствии. `verify_review_binding` реализован; `--policy-sha` подключён к fetch и publisher, `--reviews` — к promotion seal. Реализация и тесты написаны, но в рамках этого изменения не запускались. Задача #56 не считается завершённой: остаются обязательства по данным и проверка доверенного production origin.

## Целевой путь без повторной сборки

1. До сборки подготовить component reviews в `.github/release/license/reviews/components.json`. Вручную запустить `License bundle candidate` через `workflow_dispatch` на защищённом `main`, задав будущий release tag. Producer готовит source candidate, делает snapshot до сборки, собирает семь целей, записывает receipts и сравнивает встроенные notices и source info. Отдельные диагностические артефакты могут быть загружены и при ошибке. Только после успешных build и offline-tests aggregate запечатывает точные семь архивов с checksum и receipts в `license-retained-<run_id>-<attempt>`.
2. Получить из GitHub Actions **числовой artifact ID**, run ID, attempt и build commit SHA сохранённого producer run; имя артефакта и тег не заменяют artifact ID. Проверить сохранённые бинарники и evidence, затем подготовить отдельный target review для каждой из семи целей в `.github/release/license/reviews/$TARGET.json` и зафиксировать review вместе с его evidence в Git commit. Review привязан к `source_digest`, `binary_sha256`, `target` и `build_evidence_digest`; нельзя переносить его на другую сборку. `admission.py review` читает receipt и review и создаёт новый receipt; это не сборка и не публикация.
3. В будущем promotion запускается вручную на `main` с `producer_run_id`, `producer_attempt`, `producer_artifact_id`, `build_sha`, `tag`, `review_commit`. Workflow проверяет checkout review commit, скачивает и проверяет retained bytes, финализирует семь receipts, повторно проверяет origin, копирует исходные архивы без пересборки, собирает и проверяет license bundle и запечатывает `license-admitted-<run_id>-<attempt>`. `seal-promotion` получает `--reviews` и включает Git proof review; verifier сравнивает связанные с ним review и evidence с финальными receipts. Сохраняются числовой promotion artifact ID, run ID и attempt.
4. В будущем администратор задаёт repository variables ниже, включая SHA проверенного policy commit и точные IDs обеих Actions-записей. Только после устранения блокеров возможен tag на build commit: tag workflow проверяет origin, независимо выполняет license audit и после повторной проверки передаёт сохранённый promotion publisher. Publisher проверяет provenance и admission до сетевых мутаций; новой release-сборки после review нет. Новый publisher допускает no-op для опубликованного релиза только при совпадении размеров и точных SHA-256 digest всех 16 assets с promoted файлами; отсутствие digest в API приводит к отказу. Старый опубликованный релиз остаётся неизменным и задним числом не исправляется. Сейчас создание или отправка tag не предлагается.

Repository variables, используемые `release.yml`:

- `LICENSE_POLICY_SHA`, `LICENSE_BUILD_SHA`, `LICENSE_REVIEW_COMMIT`;
- `LICENSE_PRODUCER_RUN_ID`, `LICENSE_PRODUCER_ATTEMPT`, `LICENSE_PRODUCER_ARTIFACT_ID`;
- `LICENSE_PROMOTION_RUN_ID`, `LICENSE_PROMOTION_ATTEMPT`, `LICENSE_PROMOTION_ARTIFACT_ID`.

## Корни доверия и отказ по умолчанию

Production authority — защищённый `main` исходного repository и административно установленный `LICENSE_POLICY_SHA`: release checkout проверяет этот SHA и исполняет policy-код из него, а SHA кода promotion run должен совпадать с policy SHA. GitHub API проверяет repository, workflow, успешные run/job/attempt, identity и срок artifact; код сравнивает API SHA-256 digest с digest скачанного архива. Соответствие этих digest на реальном PR run здесь не проверено. Если API не предоставляет необходимые данные доверенного producer main run, digest отсутствует или не совпадает, gate отказывает, а не доверяет локальному manifest. Project Git object привязан к build commit и API head; SDK фиксирован checkout commit `e754abaa88ce4f9745b4729652789ffc57f8ba4c` и проверяемым SDK tree. `source_inventory.py` — интегрированный Git helper: provenance вызывает проверку исходников и Git proofs. PR runs и synthetic fixtures не являются production authority.

Git proof в `GIT-SOURCES.json` подтверждает самосогласованность записанных source metadata и bytes, но сам по себе не устанавливает доверенное происхождение: для этого отдельно необходима проверка origin через доверенный production run и GitHub API.

`verify_review_binding` проверяет Git proof review commit и точные использованные review/evidence bytes относительно финальных receipts, не исполняя код из review checkout; отсутствие или несовпадение proof ведёт к отказу. Проверка происхождения подтверждает идентичность данных, а не правильность юридических выводов человека.

## Evidence и открытые обязательства

Component review содержит выбор лицензии, обоснование, obligations и ссылки с SHA-256 на notices, evidence, retained notices и corresponding source для каждого компонента. Target review связывает четыре вида evidence: `native-link-inputs`, `platform-toolchain-inputs`, `build-input-correspondence`, `recipient-source-availability`; проверяющий должен оценить их по каждому target и компоненту. Отсутствующие или неподдерживаемые данные остаются блокерами, а не автоматически разрешаются.

Существующих Cargo metadata, build logs, hashes, найденных license-файлов и linkage diagnostics недостаточно для полного native/static linker input trace или происхождения platform SDK. Требуются недостающие доказательства native inputs, проверка MPL corresponding source и изменений, CDLA и обязательств распространения данных, а также происхождения vendor и сохранённых vendor notices, включая CCADB, по каждому затронутому компоненту. Synthetic evidence и NOTICE не являются юридическим доказательством. Никаких юридических гарантий нет; собственная MIT OR Apache-2.0 лицензия не заменяет проверки зависимостей или cargo-deny.

Snapshot раскрытых registry sources производится до build и сравнивается после него; native logs содержат диагностические output/stderr/timestamp и hashes outputs, но не полный linker trace. Для устранения цикла самозависимости component review project component digest исключает файлы review control; они остаются в source archive. При этом receipt `source_digest` включает точные байты всех файлов исходного build commit, включая review files, а также `SOURCE-MODES.json` и полный `GIT-SOURCES.json` proof: изменение review или Git metadata меняет общую identity. Git checkout отключает `core.autocrlf` через окружение для согласованности байтов между платформами.

## CI: границы проверок

Workflow содержит две дополняющие друг друга проверки. PR-only `test_lifecycle.py` выполняется для каждой из семи целей после реальной сборки: сверяет candidate с checkout commit и pinned SDK, snapshot и встроенные отчёты, проверяет запись и review receipt с TEST ONLY evidence, сохранение component blockers, отказ при неверной identity, изменённом snapshot и подмене SDK source, а также неизменность входов. Синтетические lifecycle reviews не предназначены для retained artifact.

Обязательный для всех событий offline suite `test_release_chain.py` — **TEST-ONLY transport chain**, не production authority. Он использует synthetic minimal project и архивы семи marker binaries, но настоящий Git source proof закреплённого SDK; после checkout проекта `setup-local-sdk` помещает SDK в соседний `../resocks5`. Цепочка проверяет реальные validators и механику assemble, promotion и publisher, подменяя только внешний GH transport. Она не проверяет реальные сборки, production origin или юридическое соответствие и не публикует релиз. Отдельный `test_provenance.py` использует mocked API и также не доказывает live origin.

Обработано отсутствие родительских каталогов output; raw assemble записывает диагностику в `target/license-blockers.json`, и upload указывает именно на этот путь, а не на файл в корне. Тесты написаны, но локально не запускались; наличие шагов и тестов не означает успешного CI.

## Получатели и хранение

`--licenses` и `--source-info` встроены в бинарник; бинарные архивы не получают дополнительных файлов. Для опубликованного релиза получатель может проверить SHA-256 `tor-socks5-$TAG-license-bundle.tar.gz`, затем найти `targets/$TARGET/candidate.tar.gz` и исходники внутри него в `sources/$TAG/`. Внутренний candidate сохраняет исходный build source commit, а не более поздний review commit. «inside this bundle» в `SOURCE-INFO.txt` относится к внутреннему candidate. Сопровождающие и распространители отвечают за сохранение и передачу необходимых исходников, notices и evidence; GitHub artifact или ссылка сами по себе не обеспечивают долговременное хранение или исполнение лицензий.
