# Тестирование — сегментированный CI

## Текущий контракт (#62, выполнение не проверено)

CI использует `scripts/testing/ci_planner.py` для выбора затронутых сегментов и пакетов. Для PR используется merge-base, для push — предыдущий SHA; ручной запуск affected требует `base_ref`. По умолчанию CI всегда affected; полный план выбирается только явно — см. «Явный полный прогон» ниже. Отсутствие базы, metadata или соответствия вызывает ошибку, а не переход к полному запуску. Плановый workflow запускает ограниченные stress-, vendor- и feature-проверки, а не полную матрицу workspace. Лицензионный lifecycle выполняется только для PR.

## Явный полный прогон

По умолчанию CI всегда affected. Полный прогон выполняется в конце спринта и выбирается ТОЛЬКО (а) точным footer `CI-Full: sprint-end` отдельной строкой в сообщении любого коммита проверяемого диапазона (push/PR, включая не последний коммит), или (б) ручным Actions → CI → Run workflow с mode=sprint-full (footer в коммите не нужен).

Точный формат: строка после разбивки на `\n` совпадает с `CI-Full: sprint-end` целиком; допустим только завершающий `\r` (CRLF); без начальных/конечных пробелов; ровно один пробел после двоеточия; регистр точный. Regex: `^CI-Full: sprint-end\r?$`.

НЕ триггер: упоминание в prose сообщения/кода/diff/README, содержимое файлов, название ветки, PR description, совпадение подстроки.

Ручной mode=affected footer игнорирует (ручной выбор главнее); полный прогон на каждую обычную фичу запрещён — обычные изменения едут по диффу.

Базы сравнения: для PR `--head` — исходный `pull_request.head.sha` (не `github.sha`), а checkout — synthetic merge; planner доказывает checkout точным совпадением родителей synthetic merge (первый родитель = base, второй = исходный head); любое расхождение head/base/checkout — ошибка, произвольное родство не принимается. База = merge-base(target, source); сканирование footer идёт только по исходным коммитам диапазона; diff и граф — по merge-дереву, synthetic merge message не является триггером. Squash/merge на main — реальный push, и footer должен стоять в итоговом сообщении squash-коммита: footer исходных PR-коммитов при squash теряется, в PR description он не ищется. Ручной affected: `base_ref` — произвольная валидная точка сравнения, требование предка не применяется; footer не сканируется.

Дерево плана: diff, Cargo graph, real-Tor контракт, обязательные документы и capabilities читаются из одного дерева — фактического checkout (для PR — synthetic merge); base диффа — merge-base его истории. Сканирование footer — только по исходным коммитам base..source-head, synthetic merge message исключён. Точные родители checkout доказывают Git-историю, но не равенство деревьев, поэтому план целиком считается по checkout.

Неправильная/недоказанная база (не предок HEAD при push, force-push, неизвестный ref) = ошибка плана, а не FULL и не пустой зелёный план; для PR берётся merge-base, для push — event.before с проверкой предка; синтетическому merge message PR доверия нет — сканируются только исходные коммиты диапазона.

```bash
git commit -m "тема" -m "CI-Full: sprint-end"
```

При переносе на ветку с лицензионным workflow задайте его job `required` имя `License required` и настройте защиту ветки на оба различных check: `CI required` и `License required`. В текущей ветке лицензионного workflow нет.

Хук pre-push сохраняет проверки форматирования и структуры и запускает clippy, тесты и doctest для тех же запланированных Rust-пакетов. `FULL=1` — явное локальное переопределение; ветки, теги и ошибки не приводят к полному запуску. Для новой ссылки хук использует merge-base с `origin/main` и сообщает об ошибке, если он недоступен. Обёртка требует `--base <ref>`, если явно не указан `--full`. Выбор сравнивает коммиты, а не незакоммиченные изменения; команды выполняются на рабочем дереве. Push коммита, отличного от HEAD, нескольких коммитов или с несовместимыми базами отклоняется. Push только с удалением ссылок пропускает проверки. Регрессионная самопроверка выполняется в CI, а не в хуке.

```bash
git config core.hooksPath .githooks
scripts/testing/test-affected.sh --base origin/main --mode list
scripts/testing/test-affected.sh --base origin/main --mode args
scripts/testing/test-affected.sh --base origin/main --mode run --kind all
TEST_AFFECTED_DRY=1 git push
FULL=1 git push
```

`git push --no-verify` обходит хук; используйте его только в экстренном случае. `cargo nextest` не выполняет doctest, поэтому они запускаются отдельно. `saturating-time` исключён из doctest, поскольку его примеры могут зависнуть в Windows.

Запускайте `--all-features` для vendored crate отдельным вызовом cargo, не вместе с пакетом приложения: объединение features иначе может привести к несовместимой комбинации upstream features.

## Нестабильные тесты

Профиль `ci` не повторяет упавшие тесты. Для расследования используйте `cargo nextest run --profile flaky-hunt --stress-count N` или `--stress-duration 1h`. Наборы с сокетами и остановленными часами используют группу `sockets-and-clocks` для ограничения параллелизма.

Историческая модель уровней и измерения сохранены в [`docs/plans/test-tiers.md`](../plans/test-tiers.md). Эти изменения и их выполнение в CI не проверены.
