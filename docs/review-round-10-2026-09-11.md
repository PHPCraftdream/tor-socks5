# tor-socks5: ревью правок и новый раунд P0–P3

Дата: 2026-09-11. HEAD: `6628762`. Правки: `08b80d3..6628762`.
Предшествующий отчёт о коммитах содержал TS9-01; поэтому новый раунд обозначен 10.

Проверены diff всех 19 изменённых файлов, связанные пути прогрева CLI/Android,
CandidatePool/fetcher, coalesced DNS, публикация кеша, новые тестовые оракулы.
Дополнительно просмотрены SOCKS5/upstream, аутентификация и границы серверного runtime.
Это ручное ревью указанного объёма, не полный аудит всех зависимостей и платформ.
Production-код и тесты не изменялись. Автоматический цикл исправлений не запускался.

## Результат

P0/P1 в проверенном объёме не обнаружены. Открыты два P2 и один P3.
Два замечания продолжают прежние находки, одно найдено при новом ревью.

| ID | Приоритет | Происхождение | Находка |
|---|---|---|---|
| TS10-01 | P2 | Остаток TS9-01 | Новая пауза всё ещё не доказывает атомарность check + write |
| TS10-02 | P3 | Остаток TS8-04 | Sweep раз в 64 вставки снижает константу, но сохраняет зависимость от размера реестра |
| TS10-03 | P2 | Новое ревью | Новый obfs4 cert отбрасывается как дубликат старого |

## Ревью внесённых исправлений

- TS8-01: production-проверка поколения и запись остаются под одним mutex;
  этот механизм корректен. Замечание TS10-01 касается доказательства в тестах.
- TS8-02: `warm_bridge` сопоставляет фактический `ChannelMethod` с запрошенным;
  CLI/Android принимают только `Ok(true)`. `Ok(false)` не записывается как успех.
  В `drain_pool` доступный кандидат без подтверждения возвращается в deferred.
- TS8-03: `prioritize` теперь использует тот же полный ключ WebTunnel, что merge.
  Стабильный порядок сохраняется. Регрессии этой правки не обнаружены.
- TS8-04: удаление завершённой cell с проверкой её идентичности полезно и корректно;
  оставшаяся полная очистка описана ниже.
- `6628762`: общий lock охватывает тесты сохранения/загрузки и flush, устраняя
  показанный механизм взаимного загрязнения глобального DNS store. Текущий прогон
  прошёл; один успешный прогон не является доказательством отсутствия всех флейков.

## TS10-01 — P2: тест пропускает исходную перестановку check/lock

Места: [store_cached_if_generation](../packages/bridge-probe/src/dns.rs#L352),
[тесты flush](../packages/bridge-probe/src/tests/probe_coalesce_tests.rs#L561),
[пауза](../packages/bridge-probe/src/dns_publish_pause.rs#L60).

Пауза перенесена внутрь функции, но всё ещё стоит перед mutex И проверкой
поколения. Тест делает flush, пока publisher стоит на этой паузе.
Контрпример — следующий неверный порядок внутри функции:

```text
pre_publish_pause()
if generation != expected: return false
lock(cache)
insert(answer)
```

Оба теста по-прежнему отвергнут старую запись: проверка после снятия паузы уже
увидит новое поколение. В production при этом снова возможно переключение
потока между check и lock, flush и последующая устаревшая запись.
Имена тестов «after_the_generation_check» этого не обеспечивают.

Нужен тест, который наблюдает именно критическую секцию/состязание с flush,
и отрицательный контроль с переносом проверки перед lock, оставляя hook на месте.
Подтверждено разбором порядка операций; эта мутация в рабочий код не вносилась.

## TS10-02 — P3: фиксированный интервал не устраняет полные сканирования

Места: [вставка и retain](../packages/bridge-probe/src/probe/dns_resolution.rs#L325),
[лимит одного batch](../packages/bridge-probe/src/probe/batch.rs#L29).

При H незавершённых разных lookup реестр растёт, а каждая 64-я вставка сканирует
его целиком под общим mutex. Сумма работы на заполнении — порядка H²/64,
а не заявленные O(H). При постоянно непустом реестре высокая capacity сохраняется:
`shrink_to_fit` выполняется только после полного опустошения.

`MAX_INFLIGHT_PROBES` ограничивает один `probe_all_with_policy`, не число всех
одновременных вызовов/пакетов. Semaphore DoH ограничивает отдельные запросы,
но запись в реестр создаётся до ожидания этих запросов.
Поэтому комментарий о глобальной границе не доказывает постоянный размер.
Исправление улучшает обычный случай, но TS8-04 полностью не закрывает.

Нужна ограниченная по работе очистка либо доказанный общий предел admission.
Нагрузочные прогоны не выполнялись: вывод следует из цикла вставок и retain.
Старый тест `sweeping_dead_entries_never_drops_a_still_inflight_lookup` также
не обеспечивает попадание на кратную 64 вставку; его успешность теперь не
доказывает выполнение sweep. Это пробел проверки того же механизма.

## TS10-03 — P2: ключ obfs4 не включает серверный cert

Места: [key_of](../apps/socks5-proxy/src/candidate_pool.rs#L52),
[merge/exclude](../apps/socks5-proxy/src/candidate_pool.rs#L124),
[dedup fetcher](../packages/bridge-fetcher/src/dedup.rs#L15),
[исключение working set](../apps/socks5-proxy/src/fetch_merge.rs#L146).

Для obfs4 ключ содержит transport/address/fingerprint, а дополнительная часть
WebTunnel равна None. Два валидных cert с одинаковым node ID и разными
публичными obfs4-ключами получают один ключ dedup. Сервер может сменить
obfs4-ключ, сохранив адрес и Tor fingerprint.

Если старая строка уже в pool/working config, свежий cert из источника
отбрасывается. Если обе строки в fetch-результате, побеждает первая.
Клиент продолжает использовать устаревший ключ и не проходит handshake,
несмотря на наличие актуальной строки у источника.
Существующие `merge_dedups_and_excludes_working` и `dedup_removes_exact_duplicates`
даже закрепляют слияние строк с различающимся cert; это не точные дубликаты.

Нужно различать криптографически разные obfs4 endpoints или явно заменять
устаревшую конфигурацию свежей по обоснованному правилу. Одно изменение
`prioritize` недостаточно: до ранжирования свежая строка может уже потеряться.
Сценарий подтверждён ключами и ветвями merge; живой мост не использовался.
