## TS3-01 — P1: кеш паролей не связан с текущим хешем аккаунта

**Место:** [verify и кеш:151–202](../packages/auth/src/state.rs#L151-L202),
[замена реестра:255–317](../packages/auth/src/state.rs#L255-L317).

`verify` получает актуальный PHC-хеш пользователя, но `verify_with_cache`
сначала проверяет кеш, зависящий только от имени и пароля. Совпадение
немедленно возвращает `true`, не сопоставляя запись с переданным хешем.
При TOFU-входе `resolve_init` перечитывает и заменяет весь реестр пользователей,
но кеши других аккаунтов не инвалидирует.

Контрпример: Alice входит со старым паролем и заполняет кеш; CLI меняет её
пароль в файле; первый вход Bob с `hash = init` загружает этот файл и
устанавливает новый хеш Alice в память. Следующий вход Alice со старым
паролем всё ещё принимается. Это не просто отсутствие hot reload:
новый хеш уже находится в авторитетном реестре процесса.

**Исправление:** связывать кеш с версией credential или с самим PHC-хешем.
После дорогой проверки учитывать возможную смену реестра перед публикацией
результата. Одного `cache.clear()` при reload недостаточно: ранее начатая
проверка может снова записать устаревший результат после очистки.

**Регрессия для исправления:** описанная последовательность с двумя аккаунтами;
старый пароль отклоняется, новый принимается. Управляемым барьером проверить
также завершение проверки старого хеша после reload.

## TS3-02 — P1: credentials источника уходят на другой origin при редиректе

**Место:** [запрос и переход:225–270](../packages/bridge-fetcher/src/http.rs#L225-L270),
[контракт Source:15–37](../packages/bridge-fetcher/src/fetch.rs#L15-L37).

Каждый hop вызывает `build_get_request` с исходными `headers` и `cookies`.
При абсолютном HTTPS `Location` host и port могут измениться, но проверки
origin нет. Поэтому источник с `Authorization: Bearer ...` и session cookie,
вернувший редирект на другой сервер, передаёт ему те же credentials.
Source прямо предусматривает API-токены и cookies отдельного коллектора.

Условия: настроены credentials и получен переход на другой origin,
например через открытый редирект источника. Новый сервер должен пройти
обычную TLS-проверку; обход TLS из этого кода не следует. Рекомендации
по пересмотру чувствительных заголовков при редиректе описаны в
[RFC 9110, §15.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4).

**Исправление:** учитывать нормализованный origin, включая port; по умолчанию
не переносить credentials источника через его границу. Нестандартные
заголовки с API-ключами тоже требуют политики, поэтому удаления только
`Authorization` недостаточно. Разрешённый перенос должен быть явным.

**Регрессия для исправления:** два HTTPS origin и цепочка редиректов;
первый получает credentials, второй — нет. Проверить тот же host с другим
port, относительный переход и явно разрешённый перенос.

## TS3-03 — P2: Android сохраняет независимые снимки одного BridgeStore

**Место:** [probe:155–180](../packages/android-ffi/src/engine_bridges.rs#L155-L180),
[warm и circuit:371–425](../packages/android-ffi/src/engine_bridges.rs#L371-L425),
[JNI source attribution:638–647](../packages/android-ffi/src/jni_engine.rs#L638-L647),
[отдельная задача проверки:569–598](../packages/android-ffi/src/engine_bootstrap.rs#L569-L598).

Writer приложения socks5-proxy не обслуживает Android FFI. Здесь probe,
warm, circuit verification и JNI source attribution самостоятельно делают
`load → mutate → save`. Circuit verification сохраняется из отдельной
задачи, а JNI может выполняться одновременно с engine.

Если A и B прочитали S, затем записали S+A и S+B, последняя запись теряет A.
Это касается счётчиков, retirement и атрибуции источников. Уникальные
временные имена уже предотвращают столкновение временных файлов, но
не обеспечивают объединение снимков. Граница этого пункта — Android-пути,
которые не охвачены введённым для CLI/daemon владельцем состояния.

**Исправление:** общий владелец мутаций в переиспользуемом слое либо
транзакция read–modify–write по пути хранилища для всех этих производителей.
Блокировка только `save` оставит потерю обновлений. Дисковый отказ не должен
молча уничтожать уже принятые наблюдения.

**Регрессия для исправления:** управляемое пересечение source attribution,
успешной проверки и retirement; итог содержит все изменения, включая
изменения, принятые во время неудачной публикации.

## TS3-04 — P2: удаление Tor из слота не останавливает производителей writer

**Место:** [shutdown:246–260](../apps/socks5-proxy/src/server.rs#L246-L260),
[clone и drain:280–325](../apps/socks5-proxy/src/tor_watchdog_health.rs#L280-L325),
[warmer:263–324](../apps/socks5-proxy/src/bridge_warmer.rs#L263-L324),
[verifier:120–128](../apps/socks5-proxy/src/bridge_verifier.rs#L120-L128).

Сервер вызывает `drain`, ждёт 500 ms и закрывает writer, предполагая, что
производители прекратили работу. `drain` лишь забирает ссылку из слота.
Warmer мог раньше получить собственный `TorTunnel`, продолжить
`warm_bridge().await` и отправить результат уже после закрытия writer.
Verifier вообще читает `active_bridges`, которые `drain` не очищает,
и может начать новый tick после этого вызова.

У задач нет возвращаемых владельцу handles и общего протокола stop/join.
Следовательно, финальная публикация writer не является границей завершения
всех производителей: поздние обновления отклоняются либо задачи обрываются
при завершении runtime. Уже удерживаемые clones продлевают жизнь Tor.
Сам `close_global` из исправления TS2-03 теперь достижим; дефект — в порядке
остановки и владении задачами вокруг него.

**Исправление:** остановить приём работы, отменить или завершить текущие
операции производителей, дождаться их задач, затем выполнить финальный
flush и join writer. Для blocking-проверок предусмотреть собственное
завершение, а не только отмену ожидающего async future.

**Регрессия для исправления:** задержать результат warmer барьером,
начать shutdown и убедиться, что его итог обработан до закрытия writer;
после stop verifier не запускает новые проверки.

## TS3-05 — P2: nativeStart может обогнать завершение nativeStop

**Место:** [проверка запуска:29–44](../packages/android-ffi/src/jni_engine.rs#L29-L44),
[остановка:313–358](../packages/android-ffi/src/jni_engine.rs#L313-L358),
[финальный статус:267–293](../packages/android-ffi/src/engine.rs#L267-L293),
[очистка tunnel:660–668](../packages/android-ffi/src/engine.rs#L660-L668).

`nativeStop` забирает handle через `guard.take()` и освобождает ENGINE lock
до отправки stop и ожидания потока. `nativeStart` проверяет наличие handle,
поэтому параллельный вызов видит свободный слот, пока старый engine ещё жив.
Отдельный `EngineStatus::Stopping` не закрывает эту проверку владения.
При 10-секундном timeout stop также теряет handle ещё работающего потока.

Старый engine позже может очистить глобальный `CURRENT_TUNNEL`, active
bridges и записать `Off` поверх состояния нового запуска. Возможна также
конкуренция двух engine за каталоги состояния. Гонка существует и при
обычном stop без timeout; timeout делает потерю владельца долговременной.

**Исправление:** сохранять в ENGINE состояние Stopping с владельцем старого
потока до подтверждённого завершения. Не разрешать start в этом состоянии;
при timeout удерживать handle. Обновления глобального состояния привязать
к поколению engine, чтобы старый callback не менял новый запуск.

**Регрессия для исправления:** удерживаемый на teardown engine и параллельный
start; новый запуск отклоняется до join. После timeout старый handle
остаётся доступен для завершения, поздний статус не затрагивает новое поколение.

## TS3-06 — P2: неудачная circuit verification не продвигает Android-очередь

**Место:** [выбор batch:533–541](../packages/android-ffi/src/engine_bootstrap.rs#L533-L541),
[сохранение результатов:418–424](../packages/android-ffi/src/engine_bridges.rs#L418-L424),
[ключ очереди:393–398](../packages/bridge-store/src/stats.rs#L393-L398).

Рейтинг due использует `last_verification_attempt`, а при его отсутствии —
`last_verified`. Android сохраняет только успешные результаты через
`note_circuit_verified_at`; для `ok == false` не меняется ни один timestamp.
Первые B никогда не проверенные, но channel-proven мосты с постоянно
неудачной circuit-проверкой остаются первыми на каждом tick с лимитом B.
Остальные мосты могут вообще не получить попытку при неизменном составе пула.

CLI уже записывает факт каждой попытки. Перенос сортировки на bounded heap
не исправляет отсутствие этого обновления у Android caller.

**Исправление:** сохранять время каждой фактически выполненной попытки,
успешной и неудачной; отдельно учитывать доказанный успех. Непроверенный
из-за отмены хвост не считать выполненной неудачной попыткой.

**Регрессия для исправления:** первые B кандидатов не проходят проверку;
после записи результатов следующий tick включает ещё не проверенные мосты.
Проверить сохранение этого порядка после перечитывания хранилища.

## TS3-07 — P2: chunked HTTP-ответ не декодируется

**Место:** [разбор заголовков:111–135](../packages/bridge-fetcher/src/http.rs#L111-L135),
[чтение тела:333–377](../packages/bridge-fetcher/src/http.rs#L333-L377),
[парсер мостов](../packages/bridge-fetcher/src/parse.rs).

`Transfer-Encoding` не разбирается. Ответ `200` с `Transfer-Encoding: chunked`
и без `Content-Length` читается до EOF, после чего размеры chunks, CRLF и
trailers передаются как обычный текст. HTTP chunks не обязаны совпадать
с границами строк: разделение `obfs4 ...` посреди слова превращает корректную
строку моста в несколько непригодных строк. Загрузка может вернуть пустой
или неполный список без ошибки декодирования HTTP.

Обязательная обработка chunked framing определена в
[RFC 9112, §7.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.1).

**Исправление:** использовать полноценный декодер тела HTTP поверх
существующего Tor connector либо добавить корректный разбор framing,
включая Transfer-Encoding, Content-Length, конечный chunk и trailers.
Применять лимит к декодированному телу и ограничить служебные данные.

**Регрессия для исправления:** одна строка моста разрезана на chunks внутри
transport и параметра, отдельно разрезаны чтения сокета; результат совпадает
с исходным телом. Оборванный chunk и недопустимое framing дают ошибку.

## TS3-08 — P2: Content-Length не проверяется при раннем EOF

**Место:** [чтение фиксированной длины:336–355](../packages/bridge-fetcher/src/http.rs#L336-L355),
[успешный возврат:375–377](../packages/bridge-fetcher/src/http.rs#L375-L377).

В цикле `while body.len() < cl` нулевое чтение вызывает `break`, а функция
затем возвращает `ResponseBody::Ok`. Ответ с `Content-Length: 1000`, телом
из одной полной строки моста и корректным закрытием TLS до остальных байтов
принимается как успешная загрузка частичного списка. Верхний слой не получает
сигнала, что источник передал неполный ответ.

Для ответа с заявленной длиной раннее закрытие означает неполное сообщение;
см. [RFC 9112, §6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3).
Это отдельная ветка от chunked-декодирования TS3-07.

**Исправление:** возвращать ошибку неполного тела, если EOF наступил раньше
заявленного количества байтов. Успех разрешать только после выполнения
условий завершённости выбранного framing.

**Регрессия для исправления:** заявленная длина больше фактической на один
байт; тело заканчивается как посреди строки, так и после полной строки
моста. Оба случая дают ошибку; точно совпадающая длина принимается.

## TS3-09 — P3: offload публикации оставляет глубокий clone на async worker

**Место:** [обычная публикация:458–466](../apps/socks5-proxy/src/bridge_store_writer.rs#L458-L466),
[финальная публикация:253–257](../apps/socks5-proxy/src/bridge_store_writer.rs#L253-L257),
[структуры хранилища](../packages/bridge-store/src/lib.rs).

`store.clone()` выполняется до `spawn_blocking`. BridgeStore содержит
`BTreeMap` с owning keys и записями со строками, поэтому это глубокая копия
всего хранилища, а не clone одного Arc. Каждая публикация занимает async
worker на O(S) работу и создаёт дополнительный снимок размера O(S), где S —
объём записей и принадлежащих им данных. Для Q публикаций стоимость копий
O(Q·S); объединение мутаций уменьшает Q, но не убирает эту операцию.

Сортировка, сериализация и дисковая запись уже вынесены в blocking worker:
это оставшийся расход после TS2-02, а не утверждение, что offload отсутствует.

**Исправление:** выбрать владение, при котором снимок создаётся на выделенном
владельце состояния вне async worker, либо использовать проверенную модель
неизменяемых снимков. Перенос одного `clone` под общий lock в blocking pool
сам по себе может лишь заменить задержку на блокировку производителей.

**Проверка для исправления:** счётчик глубоких копий и управляемый publisher
подтверждают порядок мутаций и границы работы владельца. Замеры аллокаций
и задержек выполнять отдельно; измеренного ускорения это ревью не заявляет.

## TS3-10 — P3: top-k предварительно материализует весь набор

**Место:** [due:218–229](../packages/bridge-store/src/stats.rs#L218-L229),
[healthy и ranking:275–324](../packages/bridge-store/src/stats.rs#L275-L324),
[take_best:407–435](../packages/bridge-store/src/stats.rs#L407-L435),
[verifier caller:134–144](../apps/socks5-proxy/src/bridge_verifier.rs#L134-L144).

Bounded heap ограничивает число выбранных элементов, но получает уже
собранный `Vec` всех N кандидатов. Пути ranking также собирают owning
массивы обёрток ссылок. Поэтому дополнительная память остаётся O(N),
а k=0 всё равно проходит и материализует кандидатов до раннего возврата
в helper. Комментарий об O(k) памяти описывает только heap.

Кроме того, CLI verifier передаёт `usize::MAX`, получает отсортированный
и клонированный полный due-пул, затем фильтрует active bridges и берёт batch.
Этот caller попадает в ветку полной сортировки и сохраняет O(N log N)
сравнений ради небольшого результата.

**Исправление:** принимать iterator в top-k и проверять k=0 до обхода;
фильтр допустимых active bridges применять до ограниченного отбора.
Нельзя просто заменить `usize::MAX` на batch перед нынешним фильтром:
это может вновь лишить активные мосты попыток. Сохранить вторичный ключ
для стабильного порядка равных рейтингов.

**Регрессия для исправления:** равные рейтинги, k=0/1/≥N и много неактивных
due-записей перед активными. Отдельно подтвердить, что буфер кандидатов
ограничен k; текущий результат сортировки можно использовать как oracle
порядка, но не как доказательство требуемых затрат памяти.
