## TS11-01 — P2: основной config вновь склеивает разные endpoints

Место: [BridgesConfig::parsed](../packages/proxy-config/src/lib.rs#L586).

Парсер использует HashSet `(transport, addr, fingerprint)` и сохраняет первую
строку. Поэтому две строки одного relay с `cert=A` и `cert=B` становятся одной.
Аналогично теряется WebTunnel-вариант с новым path, servername или addr override.
Свежая строка может успешно пройти исправленный fetcher/pool и попасть на диск,
но следующая загрузка config снова отбросит её в пользу устаревшей первой.

Воспроизведено через настоящий публичный `Config::bridges.parsed()`:
две obfs4-строки с различными корректными по длине cert дают 1 запись;
две WebTunnel-строки с `/old` и `/new` также дают 1 запись.

Исправление: полный endpoint key при разборе config. Проверять не только
dedup отдельно, но и путь fetch → promote → запись → повторный parsed.
Это соседний, ранее не покрытый этап TS10-03, а не регрессия его локального ключа.

## TS11-02 — P2: health от старого cert приписывается новому

Места: [BridgeStore key_of](../packages/bridge-store/src/lib.rs#L198),
[запись наблюдений](../packages/bridge-store/src/observe.rs),
[применение retirement](../apps/socks5-proxy/src/tor_setup.rs#L69).

Дополнительная часть ключа BridgeStore есть для WebTunnel, но obfs4 cert
отсутствует. Старый и новый ключ сервера поэтому разделяют одну запись.
Успех старого канала становится успехом нового cert; после простой TCP-пробы
новая строка может экспортироваться как channel-proven. И наоборот: retirement
старой строки делает retired новую, которую setup затем исключает.

Проверочный executable через публичный BridgeStore показал:

```text
different_cert_rows=1
unproven_fresh_inherits_channel_success=true
unproven_fresh_exported_as_channel_proven=true
retiring_old_also_retires_fresh=true
```

Исправление: согласовать ключ с pool/fetcher, не переносить channel/circuit
доказательства между различными obfs4 ключами. Нужен save/load regression,
включая отсутствие чужого retirement и чужого channel_ok_count.

## TS11-03 — P2: pruning удаляет рабочий вариант вместе с отказавшим

Место: [prune_bridges_from_config](../apps/socks5-proxy/src/tor_setup.rs#L477).

`dead_keys` и сравнение внутри retain содержат только transport/address/
fingerprint. Если в config есть `/old` и `/new` одного WebTunnel relay, а dead
содержит только `/old`, функция удаляет обе строки. То же происходит с разными
obfs4 cert после ротации. Дефект остаётся даже после исправления TS11-01/02.

Контрпример подтверждён точным разбором retain; сам private helper с записью
config в этом раунде не запускался. Исправление: тот же полный ключ, что при
отборе. Regression должен оставить рабочую соседнюю строку после prune/save/load.

## TS11-04 — P2: результат старой пробы удаляет новый DNS-ответ

Места: [окончание resolve_and_probe](../packages/bridge-probe/src/probe/mod.rs#L419),
[forget_dns_answer](../packages/bridge-probe/src/dns.rs#L305).

Сценарий: A разрешил hostname в старой сети и выполняет пробу; происходит
flush; B получает и кеширует адрес новой сети; A завершается с Unreachable
и безусловно удаляет запись по hostname. Новый ответ B уничтожен, хотя A
его адреса вообще не проверял. Аналогичная гонка возможна после обновления
записи в том же сетевом поколении.

Кроме того, Unreachable у WebTunnel включает HTTP 404 и TLS/Upgrade ошибки.
Такие отказы могут быть следствием неправильного path/cert, а не DNS, но
они также сбрасывают общий кеш hostname для остальных вариантов endpoint.

Подтверждение — разбор путей и межпоточного порядка; сетевой race-reproducer
не запускался. Исправление: условная инвалидация по версии использованной
записи/набору адресов и поколению, с различением ошибок подключения и протокола.
Тест: удержать A, опубликовать B, завершить A ошибкой и проверить сохранность B.

## TS11-05 — P3: обработка больших probe-результатов квадратична

Места: [probe_measured](../apps/socks5-proxy/src/tor_setup.rs#L286),
[фильтрация alive](../apps/socks5-proxy/src/tor_setup.rs#L166),
[ранжирование](../apps/socks5-proxy/src/tor_setup.rs#L180).

- Для N мостов `filter(!round.unmeasured.contains(bridge))` стоит O(N·U);
  при U=N — O(N²), например когда резолвер недоступен для всего списка.
- `alive.retain(allowed.contains)` стоит O(A·K), а K может быть равно A.
- `sort_by_key` повторно ищет позицию через линейный `ranked.iter().position`:
  до O(A log A · R) сравнений вместо подготовленного rank index.

Ограничение startup active pool смягчает обычный случай, но fallback и
полные повторные пробы обрабатывают весь список. Лимит конкурентных проб
не ограничивает длину готовых результатов.

Исправление: один набор полных ключей unmeasured/allowed и одна map key → rank;
после подготовки — ожидаемые O(1) membership и O(A log A) сортировка. Сохранить
порядок равных элементов. Это оценка по алгоритму, не измеренный выигрыш времени;
нагрузочный benchmark не проводился.

## TS11-06 — P3: живой ключ заново аллоцируется на каждом sweep

Места: [queue_key](../packages/bridge-probe/src/probe/dns_resolution.rs#L292),
[sweep](../packages/bridge-probe/src/probe/dns_resolution.rs#L428).

Перед проверкой Weak код удаляет ключ из queued_keys, освобождая его String.
Для живой записи queue_key сразу клонирует String и вставляет его обратно,
хотя членство не изменилось. До 128 ненужных клонирований непустого hostname
на один sweep плюс повторные операции HashSet выполняются под общим mutex.

Исправление: для живой записи оставить членство в queued_keys и переместить
имеющийся ключ в конец VecDeque. Удалять marker из set только для отсутствующей
или мёртвой записи. Продвижение FIFO и ограничение посещений сохранить.
Аллокации следуют из исходника; allocator benchmark не запускался.
