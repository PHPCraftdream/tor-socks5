## Decisions
- Chose the **full warm-pool** design (parallel pre-warmed channels to several bridges) over a **cheaper reactive-only failover** (just signaling guardmgr on degradation, no pre-warming) — user explicitly picked the fuller option via `AskUserQuestion` despite the recommendation leaning toward the cheaper one.
- Implemented "soft failover" as *feeding arti's own existing primary-guard fallback machinery* (`GuardMgr::note_external_failure`, Tor guard-spec prop271) rather than building custom bridge-routing logic — arti has no public "which guard is primary right now" query, so the watchdog infers degradation from per-bridge circuit-layer health (`BridgeStore`) rather than needing that visibility.
- `warm_pool` defaults to `enabled: false` (opt-in, non-breaking) at the code level, but the user chose to turn it **on** immediately for this production deployment.
- Used `@sh` sub-agents instead of `crush` for all four implementation tasks, strictly because of the active `zai` peak-hours blackout (08:00–12:00) confirmed by two failed `crush run` attempts — not a general change in delegation policy.
- Discarded a partially-completed, uncommitted diff after a mid-session process crash and restarted both interrupted tasks from a clean repo state, per the user's explicit "redo everything from scratch" instruction, rather than trying to salvage/continue the partial work.
