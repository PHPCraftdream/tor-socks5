## TS5-01 — P2: буфер chunked reader растёт вместе с потреблённым ответом

**Место:** [read_line](../packages/bridge-fetcher/src/http/framing.rs#L71-L102),
[потребление payload и разделителя](../packages/bridge-fetcher/src/http/framing.rs#L162-L179).

После исправления TS4-10 `pre` служит refill-буфером. Он очищается только
при входе в `read_line`, если к этому моменту потреблён целиком. Если в нём
осталось начало следующей строки размера, новые данные дописываются через
`extend_from_slice`, а уже потреблённый префикс остаётся в памяти.

Конкретная последовательность фрагментов: сначала `1\r\na\r\n1`, затем
несколько раз `\r\na\r\n1`, в конце `\r\na\r\n0\r\n\r\n`.
После каждого payload остаётся начало следующего размера. Указатель
`pre_pos` движется вперёд, но длина `pre` продолжает расти. Все чанки
корректны; для проявления не нужны большие строки или неверный размер.

Reader удерживает весь полученный wire-объём в дополнение к decoded body.
Для K однобайтовых чанков с расширениями длины E это порядка `K × E`
байтов метаданных, тогда как лимит тела считает K байтов. Проверка
`MAX_SIZE_LINE` ограничивает только текущую непрочитанную строку.
Квадратичного повторного сканирования здесь нет: `scan_from` его избегает.

**Исправление:** ограничить refill-буфер, удалять потреблённый префикс перед
дозаполнением либо перейти на bounded `AsyncBufRead` с отдельным reusable
scratch для строки. Сохранить непрочитанный хвост, лимиты тела и trailers.

**Критерий проверки:** на короткой последовательности указанных фрагментов
контролировать максимальный размер внутреннего буфера, а не только decoded
результат; отдельно проверить допустимые extensions и разрыв CRLF.

## TS5-02 — P2: отмена DNS lookup не снимает ожидающие работы

**Место:** [создание detached tasks](../packages/bridge-probe/src/probe.rs#L616-L650),
[ожидание permit и timeout](../packages/bridge-probe/src/probe.rs#L563-L599),
[внешний DNS deadline](../packages/bridge-probe/src/probe.rs#L309-L322).

`race_first_answer` теперь своевременно возвращает первый ответ: задержка
TS4-04 устранена. Однако handles всех spawned attempts теряются. При
победе провайдера или истечении внешнего deadline остальные задачи
продолжают работу, включая ещё не получившие semaphore permit.

Четырёхсекундный timeout начинается **после** `acquire_owned().await`.
Лимит 64 ограничивает одновременно выполняемые attempts, но не число
ожидающих задач и не их общий срок жизни. На холодном большом пуле один
набор из 64 probes может создать 256 attempts первой волны. Следующие
запросы конкурируют с работой, чей потребитель уже завершился по timeout.
Ожидающий attempt может начать сетевой запрос уже после отмены своего probe.

Сбор статистики проигравших провайдеров явно задуман, но ожидание admission
не ограничено бюджетом запроса. Комментарий о самостоятельной ограниченности
задач не обеспечен для этой фазы. Возможны накопление очереди и задержка
актуальных запросов за работой, результат которой уже некому вернуть.

**Исправление:** общий deadline должен включать очередь; отмена владельца
должна снимать ещё не начатые attempts. Если фоновая статистика нужна,
передавать её bounded supervisor с явным владением задачами и shutdown.
Быстрый возврат победителя при этом сохранить.

**Критерий проверки:** занять единственный тестовый permit, поставить attempt
в очередь, отменить lookup и освободить permit. Отменённый attempt не должен
начинать I/O; отдельно проверить ограниченность фоновых работ после победы.

## TS5-03 — P2: наличие IPv6-кандидата ещё не гарантирует его проверку

**Место:** [WebTunnel attempt loop](../packages/bridge-probe/src/probe.rs#L379-L406),
[TCP и TLS handshake](../packages/bridge-probe/src/probe.rs#L428-L443),
[обычный TCP probe](../packages/bridge-probe/src/probe.rs#L752-L765).

Для WebTunnel один `timeout(budget, attempt)` охватывает весь цикл адресов.
Внутренние TCP, TLS и чтение Upgrade-ответа отдельного лимита попытки не
имеют. Первый blackholed адрес либо сервер, зависший после TCP accept,
расходует весь budget. Второй исправный адрес остаётся непроверенным,
а результат становится `Unreachable`.

Исправление TS4-08 теперь оставляет обе IP-семьи в списке, но при зависшем
первом IPv4 до IPv6 выполнение не доходит. Это отдельный дефект выполнения
попыток; новый алгоритм формирования списка сам по себе корректен.
Обычный `tcp_probe` уже ограничивает каждую попытку отдельно.

**Исправление:** ограничить полный TCP/TLS/Upgrade attempt на адрес и
оставлять бюджет альтернативам; рассмотреть ограниченную гонку IP-семей.
Сохранить конечный общий deadline и закрытие проигравших соединений.

**Критерий проверки:** первый адрес принимает TCP и не отвечает на Upgrade,
второй возвращает 101. Probe должен успеть проверить второй адрес; включить
вариант с разными IP-семьями и сценарий, где недоступны все кандидаты.

## TS5-04 — P2: уже непригодный DNS answer сохраняется как свежий

**Место:** [экспорт live cache и выбор победителя](../packages/bridge-probe/src/dns.rs#L439-L471),
[предел stale fallback](../packages/bridge-probe/src/dns.rs#L199-L213),
[проверка после загрузки](../packages/bridge-probe/src/dns.rs#L478-L487).

Сохранение фильтрует live cache только по непустому списку адресов и ставит
`resolved_at_unix = now`. Проверки `expires_at` нет. При этом просроченные
записи остаются в map: чтение их не удаляет, а sweep при вставке зависит от
достижения capacity. Поэтому запись старше TTL **и всего 24-часового stale
window** может оставаться резидентной и попасть в периодический save.

После рестарта такой IP принимается disk fallback ещё сутки. Даже более
новая пригодная disk-запись того же host проигрывает старому live entry:
проверка приоритета в строке 460 тоже не учитывает его возраст.

Это расширение проверки TS4-05: сохранённый fallback больше не стирается
при пустом live cache, но уже непригодный live answer способен его заменить.
Здесь проблема не в выбранной политике timestamp для недавнего ответа,
а в повторном допуске ответа, который текущий stale fallback уже отвергает.

**Исправление:** одинаково проверять пригодность live entry при экспорте и
при решении, заменяет ли он disk entry. Для строгого ограничения возраста
хранить время исходного разрешения и не продлевать его периодическим save.

**Критерий проверки:** resident live entry за пределами stale window не
попадает в save/load; пригодный disk entry того же host сохраняется.
Нынешний [тест истечения disk entry](../packages/bridge-probe/src/tests/dns_tests.rs#L365-L396)
этот случай не покрывает.

## TS5-05 — P2: HTTPS URL с IP не работает при отключённом DNS

**Место:** [connect_direct](../packages/bridge-fetcher/src/direct.rs#L63-L86),
[resolve_addrs](../packages/bridge-probe/src/probe.rs#L678-L747),
[настройки resolver](../packages/proxy-config/src/lib.rs#L51-L78).

`connect_direct` всегда вызывает `resolve_addrs`, даже если `host` уже
является IPv4 или IPv6 literal. В `resolve_addrs` отдельного пути для IP
нет. При `doh_enabled=false` и `system_fallback=false` он сразу возвращает
ошибку отсутствия resolver. Для literal нет и записи в `KNOWN_HOST_PINS`,
поэтому ошибка обрывает fetch до TCP connect.

Корректный `https://127.0.0.1:PORT/...` или HTTPS URL с IPv6 тем самым
зависит от DNS policy, хотя разрешать имя не требуется. Исправленный
TS4-07 парсер выдаёт подходящий `dial_host`, но транспортный путь это
представление до конца не использует.

**Исправление:** распознавать `IpAddr` до выбора DNS policy и строить
`SocketAddr::new(ip, port)` непосредственно. Избежать ручного соединения
IPv6 host и port через двоеточие.

**Критерий проверки:** IPv4 и IPv6 literal достигают loopback endpoint
при обоих выключенных resolver flags; hostname при той же policy
по-прежнему отклоняется. Проверка должна охватывать connect, не один URL parse.

## TS5-06 — P2: восстановление после panic теряет ранее принятые изменения

**Место:** [передача store и обработка panic](../apps/socks5-proxy/src/bridge_store_writer.rs#L350-L406),
[shutdown при отсутствии store](../apps/socks5-proxy/src/bridge_store_writer.rs#L265-L297),
[нынешняя регрессия panic](../apps/socks5-proxy/src/bridge_store_writer_tests.rs#L859-L905).

TS4-09 перенёс COW и мутацию на blocking thread. Теперь `store.take()`
перемещает единственное актуальное состояние в closure. Если следующая
мутация паникует, closure уничтожает весь owned store, а actor продолжает
работу с `store=None` и намерением перечитать файл.

Условие потери данных: мутация A уже получила `Ok` за поглощение в память,
её публикация не удалась и ждёт backoff; затем мутация B паникует.
Теряется не только B, но и подтверждённая A. Следующая мутация загрузит
устаревший файл. Если вместо неё приходит close, ветка `None => Ok(())`
может сообщить успешное завершение при оставшемся `retry.dirty`.

Кроме того, при `store=None` retry не может запустить публикацию. После
истечения сохранённого `retry_at` [timer](../apps/socks5-proxy/src/bridge_store_writer.rs#L437-L448)
повторно становится немедленно готовым, а срок новой попытки не меняется.
Это ещё одно следствие несогласованного recovery state.
Текущий тест паникует на первой мутации, когда терять предыдущую A нечего.

**Исправление:** recovery обязан сохранять ранее принятые изменения либо
переходить в явное terminal error-состояние, которое close не выдаёт за успех.
Продумать владение snapshot/транзакцией на unwind; не возвращать глубокую
копию на async worker. Согласованно завершать или сбрасывать retry state.

**Критерий проверки:** A подтверждена, publisher управляемо отказал, B
паникует. После recovery A сохраняется; если восстановление невозможно,
close возвращает ошибку, а actor не крутится на просроченном retry timer.

## TS5-07 — P3: DNS persistence занимает общие mutex форматированием

**Место:** [сериализация и запись](../packages/bridge-probe/src/dns.rs#L439-L471),
[вызов из async watchdog](../packages/android-ffi/src/engine_bootstrap.rs#L423-L440).

Под mutex live cache клонируются IP-массивы, создаются строки IP и строки
записей. Затем, всё ещё удерживая первый mutex, функция берёт mutex disk
store и форматирует вторую map. Cache hits и обновления ждут не только
чтения согласованного снимка, но и всех этих аллокаций. Объём работы
линеен по числу hosts и адресов в сохраняемом наборе.

Файловая запись уже происходит **после освобождения mutex**. Однако
`std::fs::write` остаётся синхронным и вызывается непосредственно из async
watchdog перед top-up. Задержка storage блокирует выполняющий его runtime
thread. Замедление на конкретном устройстве в этом раунде не измерялось.

**Исправление:** коротко снимать данные под locks, затем форматировать и
сохранять вне critical sections и async worker. Периодические сохранения
объединять и упорядочивать, чтобы offload не породил конкурирующие записи.
По возможности исключить промежуточный `Vec<String>` на каждый IP-list.

**Критерий проверки:** задержанный test publisher не мешает runtime task
и cache lookup; повторные запросы save не создают неограниченную очередь.

## TS5-08 — P3: channel-proven top-k полностью сортирует кандидатов

**Место:** [channel_proven_bridges](../packages/bridge-store/src/stats.rs#L19-L34),
[Android export](../packages/android-ffi/src/jni_engine.rs#L785-L795),
[существующий bounded selector](../packages/bridge-store/src/stats.rs#L416-L433).

Метод собирает все N подходящих `&Entry`, стабильно сортирует их и только
затем делает `take(limit)`. При малом k это `O(N log N)` сравнений и `O(N)`
памяти под ссылки; k=0 тоже выполняет сбор и сортировку. Метод используется
экспортом проверенных мостов, где запрошенный лимит может быть малым.

Другие selectors после TS2-06/TS3-10 уже используют bounded heap. Этот
метод в прежние находки не входил; их исправленные пути не переоткрываются.

**Исправление:** ранний выход для k=0 и streaming top-k с `O(N log k)`
временем и `O(k)` дополнительной памятью. Сохранить порядок:
`last_channel_ok` по убыванию, затем `channel_ok_count` по убыванию,
затем исходный порядок BTreeMap для равных оценок.

**Критерий проверки:** сравнить результат с прежней стабильной сортировкой
для равных оценок, retired entries, k=0, k=1 и k≥N. Выигрыш всего JNI-вызова
не равен выигрышу selector: загрузка store остаётся отдельной стоимостью.
